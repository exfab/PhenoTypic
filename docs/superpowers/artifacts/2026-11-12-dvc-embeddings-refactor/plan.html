For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

Goal: Make a PhenoTypic CLI run usable as one DVC stage by automation, with per-pipeline tables in every OME-Zarr store, and DINOv2 crop and grid embeddings stored under the pipeline that produced them.

Architecture: Six phases, each shippable on its own:

  • P0 and P1 rename files: typed config suffixes, and CSV to TSV.
  • P2 adds the run contract automation reads: exit codes, phenotypic-wait, metrics.json, schema.json, byte-stable deliverables, and a DVC how-to page.
  • P3 moves a store's tables into one folder per pipeline behind a single resolver, and every reader goes through it.
  • P4 adds the embedding producer.
  • P5 lets process mode run measurements, adds the in-place process run, and rolls the result out to AutoConvertRaw-GC.

Tech Stack: Python 3.12, pydantic v2, polars/pandas/pyarrow, zarr v3 (OME-Zarr 0.5), click, torch + transformers (the foundation extra), pytest, Slurm. The render tool is ~/.claude/tools/render_md_artifact.py.

Global Constraints

  • Canonical typed suffixes are .pht-pipe.json, .pht-op.json, .pht-cc.json and .pht-tune.json. The old .json.pht-* forms are read-only legacy. Plain .json stays legacy-readable for pipelines and tune specs.

  • A file rename never changes file bytes, so pipeline_sha256 is unchanged.

  • TSV is UTF-8, one header row, \t separator, \n line ends, with " quoting for fields containing tab, newline or quote. Generated files only; inputs accept .csv or .tsv.

  • Two generated files stay CSV until #283, because GUI code writes them (spec B9): error_analysis.csv, and the curated mirror measurements.csv, which finalize writes beside measurements.tsv.

  • deliverables/metadata.<ext> is a byte-for-byte copy of the user's input, keeping its extension. Nothing ever rewrites it.

  • DVC outs are <out>/deliverables, <out>/results and <out>/.phenotypic, all persist: true. cache.type must be reflink,copy; hardlink and symlink are unsupported.

  • Exit codes, fixed here and used everywhere (phenotypic.sdk_.RunExitCode):

    Code Name Meaning
    0 COMPLETE finished, no terminal failures
    1 ERROR a runtime or config error (today's code)
    2 — a refusal raised as a Click usage error; Click's own, unchanged
    3 COMPLETE_WITH_FAILURES finished, some images failed terminally
    4 SUBMITTED submitted to SLURM, not finished
    5 ENDED_UNPUBLISHED phenotypic-wait: no job alive, and this submission published nothing
    6 WAIT_TIMEOUT phenotypic-wait gave up after --timeout-seconds

  • Store tables are tables/<n>-<sha12>/{measurements,metadata,embeddings/<model>/{crops,grid}}/.

    • <n> is a store-local call-order counter: a new folder gets 1 + the highest number among the store's run folders and its upstream entries. Numbers are never reused, so two folders never share one.
    • <sha12> is the first 12 hex of the pipeline file's sha256, or unknown when no digest is known.
    • The descriptor is attributes.phenotypic.tables with schema_version: 2; each run entry carries order.
    • The same pipeline replaces its own folder; a different one adds a folder.

  • embedding columns are Arrow FixedSizeList<float16>[D]. They are never in master, mirror, splits or any TSV.

  • PROCESS_LAYER_SEMANTICS_REVISION goes from 4 to 5 (_cli_failure_tracker.py:214).

  • MeasureDinoEmbedding fields, in order, with defaults: size="base", version=2, regions="objects", grid=None, pooling="crop_cls", crop_px=224, crop_pad_frac=0.25, mask_background=False, dtype="float16", batch_size=64, device="auto".

  • MeasurementInfo members get label/desc only, never bio_desc.

  • Heavy imports (torch, transformers) stay inside functions. The startup-import guards in tests/unit/ci/ must stay green.

  • sdk_ never imports _cli. tests/unit/sdk_/test_run_state_layering.py enforces this.

  • No file under src/phenotypic/_gui/ changes (GUI deferred to issue #283).

    • Every name the GUI imports from phenotypic.sdk_ stays defined, and every sdk_ function the GUI calls keeps its name and signature. P1 T1's AST guard (tests/unit/sdk_/test_gui_sdk_imports.py) enforces this.
    • Other GUI breakage is accepted until #283. The GUI tests it turns red stay red: no xfail, no skip, no edit to a GUI test.
    • Expected-red GUI tests are listed below. A phase gate treats exactly that list as expected-red. Any other red GUI test is a real failure.

  • Merge gate: #281 does not merge to main until #283 has fixed every known GUI break (spec §2.2), including the run console's reading of exit code 4 (_gui/run_console/_slurm.py:826) and every expected-red test below.

Review Focus

Inputs and conditions the spec implies but no feature test would hit by accident. Each one is pinned by a test in the task named.

  1. A tree written before this change is opened by the new code. That covers old .json.pht-pipe names, measurements.csv and v1 flat tables/. Readers must still work; forward modes must refuse a v1 store with a pointer to --mode migrate; and a v1 tree that read complete must still read complete after migrate. Pinned in P0 T1, P1 T4 and P3 T5.
  2. A staged GPU run re-runs Stage 1 over a store that already holds crop embeddings. The all-zeros Stage-1 objmap must not permanently mark the entry stale, and the table-less Stage-1 save must not drop the folder. Pinned in P3 T2 (test_stale_is_recomputed_not_latched, test_table_less_save_keeps_its_own_folder).
  3. The same --output is run again with an edited pipeline, or measured again. A full run with A then A′ must give folders 1- and 2-; measure with the same pipeline must leave one folder and the same row count; measure with another pipeline must add a folder and leave the first byte-identical, and a later recompile must keep the second pipeline's measurements. Pinned in P3 T2, T3 and T4.
  4. The SLURM finalizer dies (OOM or cancel) and the lifecycle fence stays active, or a measure resubmission leaves the previous run's proof current. phenotypic-wait must keep waiting while any job is live, then exit 5 unless this submission published. Pinned in P2 T2.
  5. An in-place process run meets a store whose root changes under it (an AutoConvertRaw-GC reprocess, or a second writer). The run must rebuild once from the new root or fail the image, never swap a root built from stale bytes, and never rewrite a pixel. Pinned in P5 T3 (test_root_changed_before_swap_rebuilds_once_then_fails).

Spec: Part D (D1–D10)

docs/superpowers/plans/2026-11-12-dvc-embeddings-refactor/p3-tables-v2.md

Goal: Each store holds one folder per measuring pipeline, tables/<n>-<sha12>/, and every writer carries the other folders across.

Approach: All 27 modules that touch today's flat layout reach a run folder through one resolver. That makes the change a mechanical substitution at each call site, not 27 separate path joins. v1 stores are converted by --mode migrate, and forward modes refuse them.

Folder numbers are a store-local call-order counter (spec D2). A new folder gets 1 + the highest number among the store's run folders and its upstream entries. The journal's sequence is never used: it is len(applications) + 1 of one image's journal (_core/_provenance.py:374), and a forward run builds that journal from its input (_cli_process_single.py:300-321), so over a raw input it is always 1.

Which folder a writer owns (spec D6): an existing folder with the writer's pipeline sha256 is replaced, keeping its number, with every file rewritten as a new inode. Otherwise the writer adds a folder with the next number. A write with no known sha replaces the highest-numbered -unknown folder.

Which folder a reader uses (spec D6a): finalize, recompile and measure aggregate, per image, the folder that image's completion marker certifies. Readers without a record default to the highest-numbered folder that holds measurements.

  • Step 1: Run the HPCC smoke pilot. Use configs/smoke-hpcc.yaml, which writes only under data/acr-hpcc-test/, with arrays on intel. Never use data/ and never preempt.
  • Step 2: Record per-image process_s, process_peak_rss_mb and the grid-table size, from the worker's metrics files. Set processing.timeout_s and the GC memory_mib from the measured p95.
  • Step 3: Check one pilot store independently. Run zarr.open_group(store, mode="r"), read the grid table with pq.read_table, and confirm its row count equals the number of grid cells.
  • Step 4: Measure CPU determinism. Process one image twice, on two different CPU types (an intel node and an epyc node), and compare the grid table's bytes. Process-store bytes feed downstream work ids. If they differ, record the limit in docs/source/how_to/pages/zarr_storage.md: a reprocess on another CPU type re-derives downstream work.
  • Step 5: Ask the user whether to backfill existing done images with --reprocess-changed. Every image becomes "changed", because the pipeline bytes changed, and the backfill reruns calibration and BM3D denoise. Report the measured per-image cost when asking.
