The defect

PhenoTypic splits a GPU pipeline into three stages so a GPU node isn't occupied by CPU work: preprocess on CPU, infer with a resident model on the GPU, then measure back on CPU. Whether that engine engages at all comes down to one predicate:

# src/phenotypic/_cli/_cli_validation.py:147
return any(isinstance(op, GpuDetector) for op in pipeline.get_ops().values())

get_ops() returns the top level. The production pipeline puts its Sam2 inside a CompositeDetector, where it is merged against a ManualPointDetector by mutual overlap. Measured against the real config:

top-level ops: [CropImage, DenoiseBlockMatch, CompositeEnhance, CompositeDetector,
                MaskFill, MaskDilation, SmallObjectRemover, KeepSectionLargest]
composite.ops: [Sam2, ManualPointDetector]
pipeline_requires_gpu  -> False
split_pipeline_at_gpu  -> ValueError: no GpuDetector in pipeline

Nothing raises. Three consequences follow from that single False, and each one is a quiet downgrade rather than a stop:

ConsequenceSite
Staged engine never engages_cli_execution_strategies.py:1341
SLURM never adds slurm_gpus_per_node=1; the array lands on a CPU partition and device="auto" resolves to CPU:906
effective_n_jobs stays at --njobs (default -1), so N processes each build a SAM2 model on one GPU:341, :361

This is a wrong-answer bug, not a slow path. The run finishes and reports success.

The mechanism

The splitter assumes a flat sequence it can cut at an index. A nested detector is a leaf in a tree — there is no "ops before it" inside the composite, and its sibling branches have to run and merge in the same call. But the Stage-2/Stage-3 contract is narrower than it looks: Stage 2 emits exactly one (H,W) array per image, and Stage 3 replays it. Nothing in that requires the detector to be top-level. Only the split and the injection point do.

What the review changed

An independent reviewer read the plan against the tree and returned twenty findings. Five would have stopped execution on contact, and two of those were defects in the design, not the plan.

The mitigation that reproduced the bug it was fixing

The spec prescribed set_provenance_status(image, "in_progress") to escape a provenance trap. But _append_application accepts only {"complete", "failed"} — "in_progress" is non-terminal too, so it raises the exact error it was written to prevent. The probe committed alongside the spec reproduced the trap and stopped there; it never exercised the cure. An untested mitigation shipped as settled.

The real mechanism is continuing_provenance_application, which raises the owner depth so the apply joins the open application instead of appending.

A refusal production could never reach

The plan refused a GPU detector in a measurement slot — but only under a strict=True argument that just one caller passes, and that caller runs only after pipeline_requires_gpu has already returned True. A detector hidden there would return False and run silently on CPU: the very bug being fixed, reintroduced one layer down. The plan's own test passed, because it called the helper directly.

A correction that went the other way

I believed the plan's _branch_prefix was wrong and the spike's version — the one that actually passed — was right. The reverse is true. The spike lacks a root guard on its final block, so for a top-level detector it returns every preceding top-level op as the Stage-2 prefix: ops Stage 1 has already applied and written to the store, which Stage 2 would then re-run on top of themselves. All three spike shapes nest, so nothing exercised it. Passing tests said nothing about the shape they never ran.

The remaining three blockers: the Stage-2 prefix raised on a "staged" journal because image.copy() carries it; the provenance identity hook covered two of four fields, and the two it missed are pinned by an existing integration test; and the tests couldn't deserialise their own fixture, because from_json resolves classes by bare name against the phenotypic namespace.

Scope beyond staging

Two decisions reach past the immediate fix. Both change shipped, documented behaviour, and each creates a version boundary.

The objmap export now means what the pipeline says

--mode process --layer objmap wrote the detector's raw mask and stopped. For this pipeline that would be SAM2 alone — no overlap merge, no MaskFill, no SmallObjectRemover. It now runs the post-detector chain, for nested and top-level detectors, on the principle that the operations a user supplies as parameters should be the operations that actually run.

That silently invalidates in-flight continuations, because the work-id digest hashes only user configuration and knows nothing about a change in PhenoTypic's own semantics. A revision constant now rides in the process-only half of the digest — not the base payload, which would have cold-started every full and measure run on the cluster for no correctness gain.

Provenance step paths descend uniformly

They didn't. A nested ImagePipeline descended; a CompositeDetector didn't. Nested composites produced five journal entries under one identical path — two different composites with different mode values, indistinguishable by path.

Fixing it costs one pipeline_step push in four container classes, and buys something the staging work needs anyway: the walker's gpu_path and the recorded pipeline_step_path become the same value, measured identical across all three shapes. One addressing scheme instead of two kept in step by hand.

Bounds

  • Refused, loudly: more than one GPU detector anywhere in the tree; a GPU detector in meas/post/filters/model, which Stage 3 runs on a CPU node; a GPU detector inside an enhancer container, whose branch must produce a layer rather than an objmap.
  • The branch prefix runs twice — once in Stage 2, once in Stage 3 — so it must be deterministic. Zero cost for the production pipeline, whose prefix is empty; it only bites if DenoiseBlockMatch or FocusEdgePhase later moves inside the composite branch.
  • Known gap, recorded not papered over: a nested pipeline's own meas slot is never walked, so a GPU detector hidden there is neither staged nor refused. Not reachable from the builder, no known user.
  • One GPU detector per pipeline — deferred, not a limit of the design. See below.

Robust at depth

Multi-level nesting needs no new machinery. The walker, path resolution, substitution, the slot id, the cut at gpu_path[0], the replay stub and the step-path descent are all depth-general by construction — plain recursion with no depth term. The spike already ran depth 2 in two different flavours.

One piece is not automatically general: working out what runs, on the image the GPU detector will read, before it runs. That depends on how each container hands work to its children — and containers differ:

Why not a DAG

A dependency graph is the right mental model, and the prefix rule is a DAG traversal in miniature. But a faithful one can't be derived: enhanced above is a local variable, and FilamentousFungiDetector:413 runs a ContrastStretching() constructed inline that is not an operation in the graph at all. The edges live in imperative _operate bodies.

Building one anyway would mean every container declaring its internal dataflow, including intermediates that have no name — a large API change producing a structure that looks authoritative while being wrong wherever someone forgot a declaration. Overkill and unfaithful at once.

A closed table, and a refusal

Instead the splitter admits only composition primitives — the three classes that exist to compose other operations — and refuses everything else:

ContractChildren receivePrefix contributionClasses
"sequence"the previous child's outputthe ops preceding the branchImagePipeline
"same"the container's own inputnothing — branches are parallelCompositeDetector, CompositeEnhance
anything else—refuse, naming the classevery domain detector

A hardcoded type switch is only brittle if its fallthrough guesses. This one refuses, so a container nobody has classified produces an error naming the class rather than a silently wrong Stage-2 input.

The line is "composition primitive", not "currently classifiable"

The obvious objection to a class-keyed table is drift: it sits away from the _operate it describes. That objection doesn't hold for these three, because their child-input semantics is definitional — a CompositeDetector whose branches chained would not be a composite, it would be an ImagePipeline, which already exists for exactly that. The table restates a type contract rather than caching an observation.

It does not hold for a domain detector, even one that would classify cleanly today. FilamentousFungiDetector hands inoculum_detector the container's own image, so it reads as "same" — but that is incidental to an algorithm which also runs an inline ContrastStretching(), a destructive _subtract_background and a del enhanced_work. Nothing about being a fungus detector constrains it to keep doing that. Admitting it would cost the safety argument for one class nobody has asked to stage, so the rule is drawn by kind of class: a new detector needs no entry and no decision, because refusal is already the right answer for it.

And a contract can be tested where a declaration can only be asserted. Each "same" primitive carries a probe test that puts two recording operations in its children and asserts the second never observed the first's output. An attribute that is wrong passes every test; a probe cannot.

Worked example: a GPU detector inside the filamentous detectors

FilamentousFungiDetector(inoculum_detector=Sam2()) is supported. Its one OperationField is called at :395 as inoculum_detector.apply(image, inplace=False) — the container's own input, untouched. Contract "same", Stage-2 prefix empty, and Stage 2 reads detect_mat straight from the store exactly as it does for a composite.

TwoKFilamentousDetector is the refused one, and its _operate shows why — three fields, three different inputs:

A correction the diagram forced

An earlier draft claimed no per-field vocabulary could describe TwoKFilamentousDetector, because enhanced is a local with no identity in the graph. Drawing it shows that was too strong: "same" plus "after(<field>)" describes all three calls exactly — ② is "same", ③ is "after(branch_base)".

Which makes the refusal a scope decision rather than an impossibility — and scoping it by kind of class is the better cut. It is simpler, it is stable against a domain algorithm being rewritten, and the way forward for a user who wants SAM2 here is not a vocabulary extension but a pipeline change: run the detector as a CompositeDetector branch and feed its mask in, rather than nesting it inside the algorithm.

All of which is documented where an author will meet it, in a new contributor page — docs/source/contrib_guide/gpu_detectors.md — alongside the hook surface, the capability fields, the determinism requirement, and the rule that a detector must not assume it sees one image at a time.

Job dispatch and the life of an intermediate

Nesting changes nothing here — this is the existing staged lifecycle, and it is what the slot keying has to fit into.

How jobs are dispatched

The staged SLURM strategy submits the three stages as an afterany dependency chain under a fresh orchestration epoch. Every submission is recorded in an append-only ledger, and a successor is only believed if the ledger proves it — a controller checks for a row tokenised controller-after-<predecessor_id> rather than trusting a job id it was handed.

Only controller 0 is submitted initially. Before it launches Stage-1 chunk 0 it pre-arms a dependent recovery controller, so a controller that dies has a successor already queued rather than needing something alive to notice.

StageShapeChunking
1 & 3CPU arrays, --slurm profileceil(n_images / chunk_limit)
2GPU array of --gpu-shards resident-model workersnever chunked — a shard worker streams its whole shard on one GPU
finalizerdependent afteranysole publisher of aggregated outputs and the completion marker
 
chunk_limit     = min(MaxArraySize, submit_capacity)
submit_capacity = MaxSubmitJobs - 2   # the running controller + its pre-armed recovery

Because Stage 2 cannot be chunked, --gpu-shards exceeding chunk_limit is rejected at submit rather than silently truncated. And MaxSubmitJobs < 3 is refused outright — there is no room for controller, array and recovery.

Where intermediates land

ArtifactPathWritten by
Per-image layer stateresults/<ds>/zarr/<stem>.ome.zarr/Stage 1 — durable, it is the run output
Raw detector output.phenotypic/progress/stage2_raw/<ds>/<slot>/<stem>.npyStage 2

Stage 2 opens the store read-only and never writes to it. Exactly one array crosses a stage boundary per detector; the CPU siblings' masks are recomputed in Stage 3 rather than carried.

How the next stage picks them up

Continuation is content-defined — no stage trusts a status file to tell it what happened. Three predicates, checked in order:

valid_stage1_store(...)        # a promoted store exists and is well-formed
stage2_result_replayable(...)  # the raw array AND its token are both present
stage3_completion_exists(...)  # the atomic completion marker for this image

Re-running the same command after an interruption is therefore the recovery procedure: each stage re-derives what is left to do by looking at artifacts, not at a record of intent.

Cleanup, and the ordering that makes it safe

The write and delete orders are deliberate mirrors:

write:   raw   →  token      # crash between: no "done" signal, so Stage 2 recomputes
delete:  token →  raw        # crash between: orphan raw, no "done", so Stage 2 recomputes

Both orders are chosen so that a crash at any point leaves a state that is recomputable, never one that claims "done" while being unreplayable. Stage 3 consumes both after re-promoting the store; the deletes are idempotent (unlink(missing_ok=True)) and wrapped in the publication commit guard, and the same pair is called from the local strategy, the objmap export, the SLURM worker and the resume path.

Gap: orphaned raws are never swept

Cleanup is strictly per image, at Stage 3. An image that never reaches Stage 3 — a terminal scientific failure, an OOM kill — leaves its raw array behind permanently. The run finalizer clears chunk, recompile-shard and analysis artifacts from .phenotypic/progress/, but nothing sweeps stage2_raw/.

At one (H, W) uint16 array per orphaned image on a 33,923-image run, that accumulates. It is a pre-existing gap rather than something this change introduces, and slot keying makes it tidier to sweep later — the orphans sit under a per-detector directory. Worth a follow-up; not a blocker.

Designing for two detectors

This ships N = 1, but "more than one GPU detector" is two different problems with very different costs, and only one of them is expensive.

AxisShapeLands on
N — detectors per roundCompositeDetector(ops=[Sam2, Dino, Manual]) — branches read the same upstream state, so none depends on anotherworker + storage layer
R — roundsCompositeA(Sam2) → MaskDilation → CompositeB(Dino) — B reads what A producedepoch-fenced controller

Generalised, a pipeline is segments — CPU(S0) → GPU(round 1) → CPU(S1) → GPU(round 2) → … → measure — and this design is the R=1, N=1 corner. An ensemble of two foundation models merged in one composite is N=2, R=1: no controller change, ever.

The execution model for N > 1

One detector at a time across the whole dataset, parallel across images within each sweep. Stage 2 becomes N sub-sweeps:

Stage 2a   load Sam2 once per worker  → sweep every image → stage2_raw/<sam2-slot>/…
Stage 2b   load Dino once per worker  → sweep every image → stage2_raw/<dino-slot>/…
Stage 3    replay both slots, composite merges, both raws consumed and deleted

Deliberately not "hold N resident models per worker". Two foundation models on one ada6000 is a memory gamble that fails late — after all the CPU preprocessing, exactly the way a Pascal placement does. One model per worker keeps the existing residency invariant and buys parallelism from array width instead of GPU memory.

The sweep is binding, at any number of rounds

A GPU round processes every image with the model resident, then hands off. It is never interleaved per image — and that holds for an intermediate detector in a multi-round pipeline just as much as for a single one.

The tempting implementation of R>1 follows one image all the way through — GPU, CPU, GPU — before moving to the next. It needs no barrier and no extra job group, which is exactly the cost that makes R expensive. It is also wrong twice over: model residency is destroyed, paying the per-image rebuild that staging exists to eliminate — R × 33,923 loads instead of R per worker — and batching becomes impossible, because a worker that only ever holds one image can never fill a batch.

So the arrows are dataset-wide barriers, not per-image transitions. That is what makes R>1 costly in scheduling while costing nothing in per-image GPU efficiency, which stays identical to R=1. An implementation that reverses that trade has optimised the cheap axis.

Batching headroom, currently unused

Today's Stage 2 obtains residency but not batching: it calls detector._collate([sample]) with a one-element list, per image. Nothing in the engine ever collates across images, so supports_batching buys nothing yet.

That is a gap rather than a decision, and it is why the sweep matters beyond present performance. A worker streaming a shard of a full-dataset sweep can accumulate samples and issue one (N, C, H, W) forward. A per-image interleave forecloses that permanently — no amount of later work recovers it.

What landed now, at N = 1

The Stage-2 signal was keyed by image alone — stage2_raw/<ds>/<stem>.npy — so exactly one array can exist per image. That single fact is what makes N>1 structural rather than additive, so it is re-keyed by detector slot now, while the change is invisible: one extra directory level, no behavioural difference.

Deferred, it would have become a layout migration of a signal a 33,923-image run depends on, forcing every in-flight run to recompute Stage 2 — GPU time, on the scarcest resource in the system. The slot id is readable and collision-proof: sanitised path segments plus eight hex of a hash of the exact path, so ops[0] and ops-0 cannot collide after sanitisation.

Two plans, in sequence

Brainstorming the nesting problem produced a second, different design. Rather than revise the reviewed plan into it, the work is split — Plan A lands first, and about 70% of it stands underneath Plan B.

What Plan B is

Every operation declares its execution as an ordered list of phases with a device tag. The default leaves everything unchanged:

_phases: ClassVar = (("_operate", "cpu"),)                       # default: unchanged, unstageable

_phases: ClassVar = (("_prep",          "cpu"),                  # a staging-aware op
                     ("_gpu_detection", "gpu"),
                     ("_post_gpu_work", "cpu"))
_child_order: ClassVar = "parallel"                              # or "sequence"
_phase_state: ClassVar = ("_inoculum_objmask", "_inoculum_objmap")

The values named in _phase_state are PrivateAttrs, ferried by the engine across a stage boundary and simply surviving on the instance in a notebook — the author writes the same code either way. That choice is load-bearing rather than stylistic: it keeps per-image state out of the constructor, out of model_fields so the walker cannot mistake it for a child, and out of model_dump — which is exactly the bug class ReplayDetector's NdArrayField would otherwise have reintroduced on every phased operation.

What that changes

  • Declaring the phases is the opt-in. The contract table, the "composition primitives only" rule and the guard test over class kinds all disappear. Refusal becomes "hasn't declared" rather than "is the wrong kind of class" — and TwoKFilamentousDetector stays refused for an obvious reason instead of an argued one, since its children have mixed order.
  • The blind spot stops being possible. needs_gpu becomes a scan of the flattened phase list, so nested GPU work is found by construction rather than by a tree walk that someone has to remember to write.
  • Each phase runs exactly once. Plan A re-runs a branch prefix in Stage 3. Measured, FocusEdgePhase at production size is 71 s and 7.4 GB peak per image — so that doubling is 669 CPU-hours across 33,923 images, and the 7.4 GB is the real OOM risk, not the 15 MB branch masks.
  • No substitution at all. ReplayDetector and substitute_at_path disappear; the GPU phase persists its result and the next CPU phase reads it.
  • Scheduling stays static, derived from the pipeline JSON before any image is touched — no per-image divergence, no dynamic round discovery.

The five Plan A tasks that don't survive are the splitter and replay machinery — precisely the pieces that exist because A has to infer an operation's internal structure from outside. Plan B removes the need to infer, so they go and everything else stands.
