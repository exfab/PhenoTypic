Pipeline Plot Bindings

How a configured figure producer is attached to an ImagePipeline, resolved into a binding, serialized without being copied, dispatched at its lifecycle, and published to deliverables/plots/ — traced through the source and verified by running it.

The parameter It is plots, not figures figures is a different thing: a method on PhtPlot that binds a subject for a renderer. The pipeline slot is plots.
MeasureFeatures → plots Yes, and two ship that way MeasureSymZones and MeasureOrientationZones are measurers and PlotImage providers. Binding keys on the meas slot.
ImageOperation → plots Yes structurally — none ship The ops slot is in the identity registry and the GPU splitter has a guard for it, but no shipped operation mixes in a lifecycle.

The one correction worth making first

An operation is not "stored into" the figures param — it is referenced from it

The mental model matters because it is what the whole design is built around. Putting an object into plots does not put a second copy of that object into the pipeline. Normalization walks an identity registry of everything already in ops, meas, post, filters, model and qc, and if the object you passed is (by is, not ==) one of those, the binding records a reference to that slot and key instead.

Why identity and not equality

Every operation is a pydantic model. Two distinct OtsuDetector() instances compare equal and dump to identical parameter dictionaries — equality could not tell "the measurer already in the pipeline" from "a second, unrelated measurer configured the same way." The comment at _bindings.py:119-121 calls this out as load-bearing, and _identity_ref (_bindings.py:357) does a candidate is plot scan.

The staged-GPU constraint on ops-slot plots

split_pipeline_at_gpu refuses a plot whose ref.slot == "ops" when that key is the GPU detector or sits before it: "staged plotting supports only post-GPU operations, measurers, aggregate slots, and inline plots" (_cli_pipeline_split.py:53-63). That guard only exists because ops-slot plot bindings are a supported concept — it is the clearest evidence in the tree that binding an ImageOperation is intended, not incidental.

Output

What actually lands on disk

A two-page PlotImage provider was run through PlotCoordinator.emit_image with dataset="ds 1". This tree is the real listing:

deliverables/ └── plots/ └── MplTwoPage/ ← binding id (class name; a slot key when ref'd) └── ds-1/ ← safe_path_component("ds 1") └── plate_01-7e9f968494db/ ← stem + sha256(dataset\0stem)[:12] ├── Colony-count.png 9326 B ├── Half.png 8472 B ├── manifest.json 381 B └── .publication.lock 0 B

The hash suffix is not decoration. safe_path_component is deliberately many-to-one and filesystems may compare case-insensitively, so two different source images could sanitize to the same name and overwrite each other. Hashing the unsanitized pair prevents that while keeping re-run paths stable (_coordinator.py:393-402).

{
  "schema_version": 1,
  "plot_id": "MplTwoPage",
  "class": "MplTwoPage",
  "pages": [
    { "key": "count", "label": "Colony count", "file": "Colony-count.png",
      "backend": "matplotlib", "metadata": {} },
    { "key": "half",  "label": "Half",         "file": "Half.png",
      "backend": "matplotlib", "metadata": {} }
  ]
}

The manifest is written last, and replaced atomically. A page that fails to save is logged and omitted while its siblings continue, so the manifest only ever lists pages that are durable on disk.

The single-page shortcut

When an image plot returns exactly one page keyed "default" — which is what normalizing a bare figure produces (plotting/_pipeline/_output.py:10) — the coordinator skips the directory-and-manifest form and writes a flat <stem>-<hash>.png beside its dataset folder (_coordinator.py:360-380). Aggregate lifecycles never take this path; they always get a directory and a manifest.

Recipe

Making an operation plot-capable

Four additions, none of which touch the operation's parameters or its serialized shape:

import plotly.graph_objects as go
from phenotypic.abc_.plotting import PlotImage, figure
from phenotypic.detect import OtsuDetector


class PlottyDetector(OtsuDetector, PlotImage):          # 1 · one lifecycle mixin

    @figure(title="Detected objects", primary=True)      # 2 · a @figure method
    def object_count(self, image):                       #     first positional = subject
        return go.Figure(go.Bar(x=["objects"], y=[image.num_objects]))


op = PlottyDetector()
pipeline = ImagePipeline(
    ops={"detect": op},                                  # 3 · normal slot
    plots=[op],                                          # 4 · THE SAME OBJECT
)
# → binding id "detect", ref {"slot": "ops", "key": "detect"}

To control the output folder name rather than inherit the slot key, pass an explicit binding instead of the bare object: 

from phenotypic.plotting._pipeline import PlotBinding, PipelineObjectRef

plots=[PlotBinding(id="detector-overlay",
                   ref=PipelineObjectRef(slot="ops", key="detect"))]

Both forms were run. The second resolves binding.plot is pipeline.ops["detect"] → True. Note that PlotBinding and PipelineObjectRef live in the private phenotypic.plotting._pipeline package — only the contracts in phenotypic.abc_.plotting and the models in phenotypic.plotting are public.

Sharp edges

Five things the source says that the docs do not

  1. A matplotlib figure cannot be returned from an @figure methodtrap

    FigureAdapter handles both backends, and the how-to page says "Plotly and Matplotlib figures are both accepted by the CLI publisher" — true of the publisher. But the @figure wrapper unconditionally calls apply_theme(...) (_pht_plot.py:192), and apply_theme sets fig.layout.template with no backend guard (sdk_/viz/figures/_theme.py:227).

    Observed: AttributeError: 'Figure' object has no attribute 'layout'. A matplotlib figure reaches the writer only by overriding inspect() and bypassing the decorator — which is how the tree demo above was made to work.

  2. The binding id defaults to the slot key, not the class namedoc drift

    docs/source/extending/pages/custom_plotter.md states the CLI writes below deliverables/plots/<ClassName>/. That holds for an inline plot only. For a pipeline-owned object the default id is ref.key (_bindings.py:165-171) — the measurer registered as meas={"sym": …} publishes to plots/sym/, not plots/MeasureSymZones/. Confirmed in the run above. But the model slot is keyless by construction (PipelineObjectRef forbids a key on it), so ref.key is None there and the class name wins after all — a bound LogGrowthModel really does publish to plots/LogGrowthModel/. The doc is right for that one case, which is why the error survived.

  3. Plot failures are swallowed on the ordinary CLI path and raised on the staged oneasymmetry

    emit_image takes strict: bool = False and logs a warning otherwise. _cli_staged_workers.py:526 passes strict=True; _cli_process_single.py:348 and :450 do not. The same broken plot therefore fails a staged GPU run loudly and leaves an ordinary run green with a logger.warning as the only trace. Every aggregate emit path is unconditionally best-effort.

  4. Plotly PNG export needs Chrome, which is absent in this environmentenvironment

    The publisher calls plotly.write_image, and Kaleido v1+ shells out to Chrome. On this checkout that raises ChromeNotFoundError → RuntimeError: Kaleido requires Google Chrome to be installed. Combined with the previous finding, a Plotly plot configured on an ordinary CLI run here publishes no images and reports success — and on the multi-page and aggregate paths it is worse than nothing: the writer catches per page and then writes manifest.json unconditionally, so a durable manifest asserting zero pages is left behind. Fix is plotly_get_chrome (or kaleido.get_chrome_sync()), once, per environment.

  5. plots has no GUI builder surfacegap

    Grepping src/phenotypic/_gui/builder/ for the slot returns nothing: the builder composes ops, meas, post, filters, model and qc, but a plot binding can only be added programmatically or by hand-editing pipeline.json. The GUI consumes bindings — _gui/_plot_refresh.py re-emits them after a mirror edit, an analysis run or a QC rebuild — it just does not author them.
