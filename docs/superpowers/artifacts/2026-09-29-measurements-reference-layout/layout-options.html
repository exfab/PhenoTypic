Measurements Reference Layout

Three ways to turn the Measurements section into an overview page with a per-operation sidebar, plus the schema package reorganization and resizable sidebars that go with it. Try each option in the mock below. Drag either sidebar edge to resize it.

status: awaiting decisionsbranch: claude/nifty-franklin-r99zhgtheme: pydata-sphinx-theme 0.16.1

What the code shows today

  • factThe navbar item is a dropdown, not a link. _templates/navbar-nav.html renders Measurements as a menu of Measurements, Metadata and Categories. The Measurements page itself is one generated page holding every schema table, about 36 of them, one after another.
  • factMeasure operations already declare their tables. Set analyzers do not. MeasureFeatures.get_measurement_infoclasses() maps each of the 11 public measurers to its schemas. SetAnalyzer has no equivalent, so a per-analyzer page needs a new declaration on the 11 analyzers that add columns. The class you called AnalyzeSet is named SetAnalyzer in the code.
  • needs a ruleSome schemas are switched on by parameter. MeasureColor adds ColorXYZ and Colorxy only when include_XYZ and include_xy are set. MeasureOrientationZones adds diagnostics only when include_diagnostics is set. So the page generator must read the class-level declaration and label these tables "optional", instead of asking a default instance.
  • needs a homeSeveral schemas belong to no single operation. OBJECT and GRID appear on every row. CURATION, ErrorCategory, METADATA_MATCH and RADIAL_EXPANSION come from the review GUI and the metadata join. ColorComposition has no active operation, because MeasureColorComposition is commented out of measure/__init__.py.
  • needs a ruleTwo set analyzers add no columns. MADOutlierRemover and TukeyOutlierRemover remove rows and return the same columns. They output a table, but the table has no columns of its own to document.
  • factMoving schema files does not by itself change the docs. The generator decides the page structure, so the reorganization is a maintainability change. It also carries a data-compatibility cost: pickled image.metadata keys record enum classes by their private module path, so moving _metadata.py or _experimental_tags/ needs new _MOVED_CLASSES rows. The import rule you asked for is now in CLAUDE.md and schema/CLAUDE.md, and has been pushed.
  • factOnly one category exists today. CATEGORIES has a single member, StartingMetrics. A Categories page will be short until more categories are added.

      Recommendation: Option B. It keeps every operation one click away as you described, and the captions separate per-colony measurements from set-level quality checks and model fits. Those are different kinds of output: one row per colony versus one row per group or strain. The captions come for free in pydata-sphinx-theme, because each generated toctree can carry a :caption:. The groups also give the schema subfolders a natural shape.

      Schema package reorganization

      Both variants keep from phenotypic.schema import SIZE working unchanged, since the new rule already routes all callers through the package. The subfolders are underscore-prefixed to match _experimental_tags/ and the rule that only __init__.py exports are public.

      S1 · Folders by stage (pairs with B)

      The only required code change is the same under both: give SetAnalyzer a get_measurement_infoclasses() matching MeasureFeatures, and declare _measurement_infoclasses on the 11 analyzers that add columns. S1 then adds a _MOVED_CLASSES row for every metadata class that moves, so pickles written today still load. RADIAL_EXPANSION is placed only once its owner is confirmed. Today it is read only by the results-viewer GUI.

      Resizable sidebars

      pydata-sphinx-theme gives both sidebars fixed widths, and I found no built-in or published option for drag resizing. Its recent work on the sidebars covers collapse and drawer behavior only (layout docs, PR 2474). A small custom script is therefore needed.

      R1 · CSS resizeR2 · Drag handle script (recommended)

      R2 applies to every page on the site, not only Measurements, because the handles attach to the theme's shared .bd-sidebar-primary and .bd-sidebar-secondary containers. The breakpoints where 0.16.1 switches each sidebar to a drawer still need to be read from the theme's stylesheet in a real build. I have not checked them yet.

      Decisions needed before implementation

      1. Which layout? A, B or C. I recommend B.
      2. Where does Metadata go? Your list omits it. Options: a fifth entry in the top block (shown in B and C), a section of Overview, or its own navbar item.
      3. Tier System page: move or include? The tier content lives in explanation/measurement_classification_system.md. Either move that page into Measurements, or include its tier section in a new page so both places stay in sync from one source.
      4. Outlier removers: list MADOutlierRemover and TukeyOutlierRemover on a short "Filters" page, or leave them out of this reference?
      5. Schema folders: S1 (move files, add pickle remap rows) or S0 (keep files flat, group in the generator only)?
