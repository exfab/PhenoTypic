Pipeline Folders in OME-Zarr

Every pipeline that writes measurements into a store gets its own folder, named by its place in the store's history and its pipeline hash. A pipeline's scalar measurements, metadata projection and embeddings all live inside that folder. This page shows today's stores beside the proposed ones, and the three ways a downstream store could relate to the AutoConvertRaw-GC store it read.

1Why copying came up: two stores in two places

A downstream PhenoTypic run never writes into its input. It reads the AutoConvertRaw-GC store as pixels and writes a separate store under its own --output. The AutoConvertRaw-GC store is write-once, and a reprocess there replaces it wholesale. So the grid embeddings and the analysis measurements are produced into two different directories. Copying was one way to put them side by side. Section 4 shows two ways that don't copy.

3Proposed: one folder per pipeline

The top-level group stays tables/, which is already part of PhenoTypic's store schema; what changes is one level below it. The folder name is <call order>-<pipeline hash>. The call order is the application's sequence in the store's provenance journal. The hash is the first 12 hex of the pipeline file's sha256, the same digest the journal, the figure run folders and AutoConvertRaw-GC already record. Inside each folder, the model names the embedding subfolder, and crops and grid are two separate tables.

Folder per pipeline

Pipelines coexist in one store. A second analysis pipeline gets 3-<its hash> instead of replacing 2-….

Embeddings under their pipeline

No separate top-level embeddings/ group. An embedding belongs to the pipeline that produced it, exactly as its scalar measurements do.

Scalar table stays separate

measurements/ inside the run keeps the scalar measurements alone, so the master, mirror, splits and TSVs never see a vector column.

Model names the folder

embeddings/<model>/, then crops/ or grid/. A second model is a sibling folder, never extra columns.

4How the result store relates to the store it read

All three keep the AutoConvertRaw-GC store untouched, and all three number the result store's own folder 2-…, because the inherited journal already holds application 1. They differ only in what the result store says about 1-….

A · Copyprevious proposal
tables/
├── 1-3f9c2a1b7d04/   copied, read-only
│   └── embeddings/dinov2-vitb14/grid/…
└── 2-a71e09c2b4f5/
    └── …
  • The result store is self-contained: hand it over, or track it in DVC, without the bucket.
  • Duplicates the grid table into every result store. It's small, and a hardlink on one filesystem.
  • The copy is a snapshot that won't follow a later AutoConvertRaw-GC reprocess.
C · Referencerecommended now
tables/
└── 2-a71e09c2b4f5/
    └── …
zarr.json → tables.upstream:
  "1-3f9c2a1b7d04": { source: "<ds>/<stem>.ome.zarr",
                      root_sha256: "…" }
  • No copy. The record names the input store and the digest of its root, so a reader can find 1-… and verify it is the same version.
  • Reading grid embeddings needs the AutoConvertRaw-GC store to be reachable.
  • A reprocessed input shows up as a digest mismatch rather than going unnoticed.
D · Nothingsimplest
tables/
└── 2-a71e09c2b4f5/
    └── …
(the journal's application 1 is the only trace)
  • Each store holds only what was written into it.
  • The journal already names the input file and its pipeline hash, but not the input store's digest. You can't tell whether the input changed afterwards.
  • Joining across stores is up to you.

Why C over A now: once embeddings live under their pipeline's folder, copying means duplicating another pipeline's results into a store it never wrote. That is exactly what you questioned. C keeps one source of truth and still makes the link checkable.

7How others store tables and embeddings in OME-Zarr

There is no canonical schema for either one. OME-NGFF 0.5 specifies images, labels and plates, but not tables. The AnnData-based table proposal (ngff PR #64), whose stated scope included low-dimensional embeddings such as UMAP, was closed unmerged in September 2023. RFC-8 (Collections and Extensibility) is under review. It deliberately does not define a table format; it gives a way to link derived data to images and allows prefixed extension types. So each tool brings its own sub-spec:

ConventionWhere it livesHow a per-object vector is storedFit for PhenoTypic
ngio / Fractal feature table<image>/tables/<name>/; the tables group's attributes list every tablea feature table tied to a label image. Its group attributes are type: "feature_table", table_version, region (path to the label image), backend (AnnData, Parquet, CSV or JSON), index_key and instance_key. Columns are featuresclosest to what PhenoTypic already does: a tables/ group, Parquet, keyed on a label. Writing these attributes on each table group would let ngio discover our tables. I haven't checked whether it reads a list-typed vector column
AnnData in Zarr (scverse, SpatialData)a table element in a SpatialData Zarr store; linked to labels through uns/spatialdata_attrs {region, region_key, instance_key}obsm/<key>, an N × D matrix per embedding. This is the usual home for embeddings in single-cell tools (X_pca, X_umap)best for scanpy/squidpy users, but a different container from our Parquet tables. Better as an optional export than as the store format
Label image-label.propertiesthe label group's JSON metadataone JSON object per label-value, with arbitrary keysfine for a class name, not for 768 floats per colony

What this means for the design: keeping vectors in Parquet under tables/ matches the most common OME-Zarr practice (ngio's Parquet backend) without inventing a new container. Interoperability improves further if each table group also carries ngio-style attributes, and an AnnData export can come later if someone needs scanpy directly. Sources: ngff PR #64; RFC-8; ngio table specs; SpatialData TableModel docs; the NGFF label schema.

8Open for your comments

  1. Which link between stores: A, C or D?My pick is C (section 4).
  2. Interop attributesDecided: the top-level group stays tables/. Open: should each table group also carry ngio-style attributes (type, table_version, region, backend: "parquet", index_key) so Fractal/ngio can discover our tables (section 7)?
  3. Re-measuring with the same pipelineShould a second --mode measure with the same pipeline replace 2-a71e…, or write 3-a71e… beside it? Replacing keeps one folder per pipeline; a new folder keeps every pass.
  4. Hash of whatThe pipeline file's bytes, as the journal records today. A formatting-only change, such as DVC's one-line JSON rewrite, gives a new folder even if no parameter changed.
  5. FiguresThey stay in figures/<UTC-date>-<sha12>/. Should they move under their pipeline's folder too, for one place per run?
  6. Grid definitionDoes a grid cell stand for a pinned colony position at fixed pixels in every rig1 image (ManualGridFinder edges in the pipeline), or can the plate move between images?

Leave a comment on any section and I'll fold it into the design spec.
