DINOv2 Embedding Feasibility

Can AutoConvertRaw-GC write DINOv2 embeddings into every OME-Zarr store it publishes, can those embeddings survive later rewrites, and can PhenoTypic gain a per-colony MeasureDinoEmbedding? Yes to all three. Loading the model is already solved in this codebase. The real work is in store persistence, table width, and where the GPU runs.

1What was asked, and the fact that splits it

R1AutoConvertRaw-GC writes embeddings

Every store the preprocessing pipeline publishes carries DINOv2 embeddings.

R2Never overwritten

A later PhenoTypic run or rewrite never silently drops or replaces them.

R3MeasureDinoEmbedding

A measurer that gives one embedding per colony inside a normal pipeline.

AutoConvertRaw-GC has no colonies to embed

It runs --mode process with the pipeline CalibrateColorRpcc → ColorDenoise, an empty meas, and write_objmap=False. No detection happens at that stage, so it can only produce image-level embeddings (a CLS token and a mean-pooled patch vector) or a dense patch-feature grid. Per-colony embeddings need an objmap, so they belong to MeasureDinoEmbedding in a later PhenoTypic run. That means two products written in two places, sharing one storage contract.

2Six ways embeddings would be lost today

Each hazard was checked against the source. Together they rule out the obvious designs: a tables/embeddings/ sibling, a group added after the store is published, and 768 extra measurement columns.

H1A store re-save starts from an empty part

_write_store_part builds a fresh .part, carries over only figure runs, and rebuilds the root attributes. Full, Stage 1, Stage 3 and process saves all drop an unknown group or attribute key.

_image_io_handler.py:1468 (carry_figure_runs), :1478 (root written last)
H2Measure and recompile delete all of tables/

The rewrite hard-link-copies the store and then removes part/tables entirely, so it can rebuild the measurement and metadata tables. An embedding table under tables/ would be lost on every --mode measure.

_measurement_tables.py:694
H3Process stores are consolidated and immutable

Metadata is consolidated inside the part, and the code says the store "is written once and never mutated". A group added afterwards is invisible to readers that use consolidated metadata. It also breaks the byte-reproducibility that the work id depends on.

_cli_process_only.py:247, _image_io_handler.py:1511
H4The root is the completion marker's anchor

Editing zarr.json in place invalidates the image's marker. Continuation then re-derives the image, and H1 drops the addition.

working-with-ome-zarr contract; ngff_.py STORE_ROOT_JSON
H5AutoConvertRaw-GC replaces the whole prefix

Publishing runs delete_prefix and then upload_tree. Anything a separate job adds to a bucket or NAS store is deleted the next time that image is reprocessed.

acr_core/worker.py:189–190
H6Wide columns spread to every deliverable

Returned as ordinary measurement columns, 384–1024 floats per colony would reach the master, the CSV mirror and the GUI. A column no MeasurementInfo enum owns is copied into every measurements_by_feature file. A single list-typed column fixes the width, but CSV can't hold it.

util/_measurement_outputs.py:96, :200
What follows

Embeddings need (a) their own namespace outside tables/, (b) a carry step in every writer, which is the rule figures already follow, and (c) to be written inside the store's own transaction, never added after promotion. Figures prove the pattern: carry_figure_runs, known_figures_schema and apply_image_figures_attributes in sdk_/_image_figures.py are a ready template.

RuleWhat it guarantees
Deterministic entry id{family}-{model}-{scope}-{12 hex of params digest}. Re-running the same config replaces only its own entry, which is an idempotent re-derivation. A different model, size or pooling gets a new id, so the two coexist.
Carried by every writersave2zarr (full, Stage 1, Stage 3), process _save_store, and the measure/recompile rewrite all copy every other entry and file across unchanged. Only --overwrite deletes them. This closes H1 and H2.
Written inside the transactionFiles land in the .part before consolidation and before the root, and the root records their sha256. The completion marker therefore covers them. This closes H3 and H4.
Bound to what was embeddedObject-scope entries record the objmap digest. If a re-detection changes the objmap, the carried entry is marked stale and readers refuse it. Otherwise relabeled colonies would silently pick up the wrong vectors. Image and dense entries bind the series and level they read.
Unknown versions carried wholeA descriptor whose schema_version this writer doesn't know is carried untouched and gets no new entry. This copies the figures rule.
Outside OME semanticsNothing goes under attributes.ome, and nothing is listed in ome.series. Third-party viewers see the same store they see today.

Vector encoding. Recommended: one Arrow FixedSizeList<float16>[D] column. It is compact, and pyarrow, DuckDB and polars (Array dtype) all read it. Wide DinoEmbedding_000…767 columns can be produced at export time for tools that need them.

The return-contract problem

A MeasureFeatures op's frame is merged into the measurement table (H6). The proposal is a thin ABC, MeasureEmbedding(MeasureFeatures). It still sits in meas, so serialization, the GUI builder and tune need no changes. ImagePipeline.measure recognizes it by type and sends its frame to the embeddings namespace instead of the merge. Called on its own in a notebook, MeasureDinoEmbedding().measure(image) just returns Object_Label plus the vector column.

The alternative is a new pipeline slot (embed, like plots). It is more explicit, but it touches serialization, the builder, tune and the slot-namespaced tree paths.

5AutoConvertRaw-GC integration

What it does today: process_one.py:118 calls process_single_apply_only_core(layer="rgb", process_format="zarr") in an isolated child process. verify_store checks the root and the figure descriptor. The worker deletes the remote prefix, uploads the tree, and writes a done marker that records pipeline_sha256. GC runs on Spot c3d-highmem-4 VMs (4 vCPU, 30 GB budget, 16.3 GB pilot peak, 612 s per image in the pilot). HPCC runs the same container as an Apptainer .sif. PhenoTypic is vendored as wheel 0.20.2.

What Option A changes in AutoConvertRaw-GC

  • pipelines/exfab_rig1.json.pht-pipe gains the embedder.
  • vendor/ gets the new wheel; pyproject.toml and uv.lock are updated.
  • Dockerfile installs the foundation extra (CPU torch + transformers), bakes in the weights, and sets HF_HUB_OFFLINE=1. Then a rebuild with tools/build_image.sh, a new pinned :<sha> and a new .sif.
  • process.py verify_store checks the embeddings descriptor the way it checks figures; run.json carries expected_embeddings (plan.py).
  • Re-pilot memory and timeout on configs/smoke.yaml / smoke-hpcc.yaml. Never on data/.

Consequences to plan for

  • Backfill is a reprocess. Adding the embedder changes pipeline_sha256, so all done images become "changed". --reprocess-changed is opt-in. It reuses a stored TIFF when one is current, but it still reruns calibration and BM3D denoise, which is the expensive step. An embed-only backfill would need Option B's rewrite.
  • Weights offline. The Batch VMs have no external IP, so a runtime Hugging Face download probably can't reach the hub. Bake the weights into the image: roughly 88 MB (ViT-S), 346 MB (ViT-B) or 1.2 GB (ViT-L) at fp32. Verify egress before relying on this.
  • Cross-CPU determinism. Torch CPU inference is not guaranteed bit-identical across instruction sets (c3d on GC vs intel nodes on HPCC). Keep embedding bytes out of anything that must be byte-reproducible, or pin deterministic kernels and measure the drift.
  • CPU time is unmeasured. Embedding a whole image at 518 px is one forward pass. A full-resolution dense grid over a roughly 6000 × 4000 frame is about 90 tiles of 518 px. Pilot both before choosing.

8Suggested order

P1 comes first because both products depend on it. P2 and P3 can then run in parallel, and P4 waits for measured CPU throughput.

P1 · PhenoTypicEmbeddings namespace

§3 contract, carry in every writer, stale binding, tests. No model involved.

P2 · both reposImage embeddings in process mode

Image-scope embedder, process hook, new wheel and container, smoke pilot, then a decision on backfill.

P3 · PhenoTypicMeasureDinoEmbedding on CPU

Measurer, pipeline routing, per-image writers, deliverables/embeddings/.

P4 · optionalGPU staging

Option B (dense Stage-2 signal) or C (Stage 4), chosen once P3's CPU timings are measured.

9Decisions only you can make

  1. What should AutoConvertRaw-GC store?Image vectors only (about 0.3 GB in total), a dense grid (0.3–9.5 TB depending on resolution and model), or both. A dense grid would let MeasureDinoEmbedding pool from the input store and skip re-running the model, but it only supports masked_dense pooling.
  2. Which model and precision?DINOv2 small, base or large, and fp16 or fp32. This sets storage (§6), container size, and CPU time per image.
  3. Per-colony pooling?crop_cls (one forward pass per colony, the best per-colony representation) or masked_dense (one pass per plate, coarse when a colony spans only a few 14-px patches).
  4. Should result stores inherit the input store's image embeddings?A full run reads an AutoConvertRaw-GC store as pixels and writes a new store elsewhere, so today the embeddings stay behind in the input store. They could be copied forward, referenced by input digest, or left where they are.
  5. Is CPU good enough for the first version?If yes, P4 waits. If GPU is required from the start, choose between B and C first, because it changes P3's design.
