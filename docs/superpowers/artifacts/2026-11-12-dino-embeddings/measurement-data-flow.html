PhenoTypic Measurement Data Flow

Every measured colony starts as one row in one image's OME-Zarr store. A finalizer then fans those rows out into the deliverables users open. This page traces that path, lists every table the CLI writes, and shows what each writer keeps or drops when it rewrites a store.

1The CLI, end to end

Every forward mode (full, the Stage 3 half of a staged GPU run, and measure) ends at the same per-image store transaction and the same finalizer. --mode process branches off before measurement and writes a different kind of store (see the note below the diagram).

The process-mode branch (what AutoConvertRaw-GC runs)

--mode process --layer rgb calls pipeline.apply() only. It writes one single-series store per input with write_objmap=False, no tables/, no image_class and reproducible provenance, and it consolidates the metadata inside the .part because "a process-mode store is written once and never mutated". Figures from bound PlotImages are the only extra payload. No master, mirror or analysis is produced.

3How a column finds its table

Inside one image

  1. Each MeasureFeatures op in meas returns a frame keyed on Object_Label. Columns are family-prefixed (Size_Area, Texture_…-deg045-scale01).
  2. pipeline.measure merges them, then appends the framework Metadata_* block and the per-object info block (Object_Label, Bbox_*, Grid_*).
  3. The merged frame becomes PreparedImageTables.measurements. Its ordered columns are recorded as measurement_columns in the root descriptor.

Across the run

  1. The master concatenates the stores. If their schemas differ, it falls back to a diagonal_relaxed concat, so stores with different measurers can share one run.
  2. The feature and category splits ask the schema which producer owns each column: MeasurementInfo enums decode headers through member_for_header, with three header schemes (static, metric_qualified, texture).
  3. A column that no enum owns becomes a context column and is copied into every split file. This matters for any wide, non-enum output.
  4. Post ops and the analysis model see the metadata-joined mirror frame, never the master.

A process-mode store, for comparison

A single series (rgb or gray), no labels/, no tables/, no image_class (so Image.load_zarr refuses it and Image.imread reads it as pixels), and journal wall-clock fields omitted so two runs on the same UTC day are byte-identical. Root metadata is consolidated. The store is valid --input to a later full run, which writes a new store in its own output folder and leaves the input store untouched.

5Several measurement pipelines, one store

The short answer: a store holds the result of one measurement pipeline. Two things in it are designed to hold several runs side by side: figure runs and the provenance journal. Everything else has a single slot.

In practice, two measurement pipelines over the same images go to two output folders, each with its own stores and deliverables. Within one run, the master tolerates stores with different columns, but each store still holds only one measurement table.

Why this matters for new payloads

Figures are currently the only payload built to survive another writer: they have their own namespace, their own descriptor, an explicit carry step in each writer, and an --overwrite-only wipe. Any new per-store payload that must not be overwritten has to follow the same pattern. The companion page, DINOv2 Embedding Feasibility, applies this to embeddings.
