Staged Run Lifecycle

How the three stages are dispatched to SLURM, where each intermediate lands, how the next stage finds it, and the ordering that makes a crash at any point recoverable.

A pipeline containing a GpuDetector does not run per image. It splits into CPU preprocess → resident-model GPU inference → CPU measure, so a GPU node is never occupied by CPU work. This page is the reference for what that produces on disk and how the pieces find each other.

Dispatch

The three stages are submitted as an afterany dependency chain under a fresh orchestration epoch. Every submission is recorded in an append-only ledger, and a successor is believed only when the ledger proves it — a controller looks for a row tokenised controller-after-<predecessor_id> rather than trusting a job id it was handed.

Only controller 0 is submitted initially. Before it launches Stage-1 chunk 0 it pre-arms a dependent recovery controller, so a controller that dies already has a successor queued rather than needing something alive to notice. No worker installs a signal handler and no worker requeues itself.

chunk_limit     = min(MaxArraySize, submit_capacity)
submit_capacity = MaxSubmitJobs - 2   # the running controller + its pre-armed recovery

Because Stage 2 cannot be chunked, a --gpu-shards value above chunk_limit is rejected at submit rather than silently truncated, and MaxSubmitJobs < 3 is refused outright — there is no room for controller, array and recovery. After a Stage-2 timeout the controller derives the remaining work from the Stage-2 signals actually on disk and submits another round.

Stage 2 opens the store read-only and never writes to it. Exactly one array crosses a stage boundary per detector. A composite's CPU sibling masks are recomputed in Stage 3 rather than carried, and the merged result becomes durable only when Stage 3 re-promotes the store.

How the next stage finds it

Continuation is content-defined. No stage trusts a record of intent to tell it what happened; each re-derives what is left by looking at artifacts. Three predicates, in order:

valid_stage1_store(...)        # a promoted, well-formed store exists
stage2_result_replayable(...)  # the raw array AND its token are both present
stage3_completion_exists(...)  # the atomic completion marker for this image

Which is why re-running the same command is the recovery procedure. There is no --resume flag, and none is needed.

The ordering that makes a crash safe

The write and delete orders are deliberate mirrors, and the invariant is stated in the source at every consumption site: "Token FIRST at every consumption site: the only reachable intermediate state must be 'no token, orphan raw'."

CrashWhat is on diskWhat happens next
✗Anothing writtenStage 2 recomputes
✗Braw, but no tokenreads as "not done" → Stage 2 recomputes and overwrites
✗Craw + token; store not yet promotedStage 3 re-runs from the raw array
✗Dstore promoted, no markerStage 3 re-runs; replay is from the raw array, never the store's own objmap, so promoting twice is idempotent
✗Emarker written; raw + token orphanedimage is complete; the orphans are inert
✗Fmarker written; orphan rawimage is complete; the orphan is inert

Writing the marker before the deletes is what makes ✗E and ✗F harmless: continuation checks the marker first, so leftover files are never mistaken for work to do. Deleting the token before the raw is what makes ✗F the only partial-cleanup state — the reverse order would allow "token says done, raw is gone", which no later stage could act on.

Gap: orphaned raws are never swept

Cleanup is strictly per image, at Stage 3. An image that never reaches Stage 3 — a terminal scientific failure, an OOM kill — leaves its raw array behind permanently. The run finalizer clears chunk, recompile-shard and analysis artifacts from .phenotypic/progress/, but nothing sweeps stage2_raw/.

One (H, W) uint16 array per orphan accumulates across a large run. It is pre-existing rather than newly introduced, and keying the signal by detector slot makes it tidier to sweep later, since orphans sit under a per-detector directory. Worth a follow-up; not a blocker.

Two things that surprise people

  • Without --wait, the CLI reports submission only. The dependent finalizer is the sole publisher of aggregated outputs and the completion marker — the submitting process publishes neither.
  • With --wait, the aggregated outputs are written twice. The autonomous strategy never sets remote_managed, so the CLI also aggregates in the submitting process while the finalizer later aggregates again. The two are serialised by a lock and read the same authorised sources, so they write the same bytes — redundant rather than divergent. That last clause holds only because shard assignment is a contiguous split; under the older strided assignment, merge order depended on the worker count and the two writers produced different bytes.
