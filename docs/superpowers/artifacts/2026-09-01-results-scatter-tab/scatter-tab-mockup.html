Scatter

A faceted scatter tab that turns plot_strain_growth_scatter.py into a live, configurable, clickable surface — and hands back the same multi-page PDF at the end.

Branchfeat/results-scatter-gui
Stacked onome-zarr-merged @ 73516a23
Date2026-09-01
StatusLocked · verified on the migrated subset · spec next

The reference script hard-codes one figure: pages by Metadata_Strain, a 4×4 grid of pH × salinity, median radius against a derived frame index, colour by biological replicate, marker by plate configuration. Every one of those seven roles becomes a dropdown. The script's output — a multi-page PDF, one page per group — stays the export, so the tab replaces the script rather than sitting beside it.

Two things the script cannot do are the reason this belongs in the GUI and not in scripts/: a point on a growth curve that looks wrong is a specific colony on a specific plate, and right now checking it means leaving the plot. Here you click it.

Third and last tab in the results-viewer tab bar, after Plate and Colony — Heatmap and QC are deprecated and no longer mounted (_layout.py wires two tabs today). It boots on the first section group with every role pre-filled from whatever the run actually has, so you get a figure before you touch a control.

Section pager. One group at a time on screen. Twelve strains × sixteen facets × a thousand points each is not a page anyone can render or read; the PDF is where all twelve land.

Two different caps, and they interact. The per-axis max_cardinality above bounds each dropdown's option list; SCATTER_FACET_CAP bounds rows × columns, the number of live WebGL contexts. A 12-value row axis crossed with a 12-value column axis is 144 panels, which no context budget survives — so the product is checked after both are chosen, and an over-cap grid renders the first N panels plus the "showing first N of M" notice rather than refusing the selection.

Cardinality caps differ by role on purpose. A section group can be any size — you page through it. A facet axis above about twelve stops being a grid and becomes a wall. Hue and shape are capped at what a legend can carry and what Okabe-Ito can keep distinguishable.

08

What the answers changed

Three follow-ons I am carrying into the spec as stated assumptions. Say the word on any of them and I'll revise instead.

1 · Over 500k points makes WebGL a v1 requirement, not a v2 feature

Plotly's SVG go.Scatter does not render at this scale — it is a dead browser tab, not a slow one, and the pager only divides the total by the number of section groups. The deferred feature was adaptive switching: measuring a threshold and choosing a trace type across it. So v1 uses go.Scattergl unconditionally, which is strictly simpler than switching — one code path, no threshold to measure — and the v2 item stays deferred as written.

Decided: the grid renders as make_subplots with gl traces, guarded by a SCATTER_FACET_CAP constant that mirrors the existing TIMELINE_COMPARE_CAP = 12 in gui/_config.py:757 — which is there for this exact reason ("browsers cap live WebGL contexts (~16 in Chrome)"). Over-cap renders the first N facets plus a visible "showing first N of M" notice, never a silent truncation, following the rule that constant already documents. The cap's value comes from spike A, not from a guess.

Fallback if the measured cap lands below 16: a pH × salinity grid is 16 panels, so a cap of 12 would break the figure this tab exists to draw. If the spike shows 16 gl subplots do not survive, the grid collapses to a single gl axes pair with per-facet coordinate offsets and drawn separators — one context regardless of facet count. More work, no ceiling. The spike decides which, before any layout code is written.

2 · kaleido plus Scattergl probably means raster points in the PDF

Kaleido renders through headless Chromium on the compute node — no display, no GPU, no client involved. So the export path needs WebGL to work headless and server-side, where it will be software-rasterized at best. Two ways this bites: the point layer very likely arrives in the PDF as a raster image while axes, ticks and legend stay vector; and in the worse case the gl layer does not render at all under headless GL.

Spike B, run first: export one real page from the Maresca run on a compute node and check that the points are present, then whether they are vector. This is the only open item that can reopen a locked decision, so it runs before anything else is built.

3 · Filters-only removes the curation write path entirely

Box-select bulk curate is dropped and Exclude colony is gone from the inspector footer — both wrote shared curation state. Scatter still reads curation, because the grey-✕ toggle you asked for needs it. The inspector is now read-and-navigate only: crop, plate context, measurements, prev/next, copy row.

09

Prerequisite: fix the crop path

The Scatter inspector is the third consumer of the shared crop route, and that route is currently broken on migrated stores. This lands as its own commit, before any Scatter code, because the Colony grid and the QC gallery are equally affected.

Bug 1 · uint16 stores render as noise

_store_layer_array_to_rgb (_shared/tiles.py:466) converts the rgb layer with a bare cast. NumPy's astype defaults to unsafe casting, so a narrowing integer conversion keeps the low byte and discards the high bits — value & 0xFF, not a scale.

  18315  0100011110001011  →  139
  18175  0100011011111111  →  255
  18176  0100011100000000  →    0   ← +1 in source, −255 in output
  31783  0111110000100111  →   39

The mapping is non-monotonic, so every crossing of a 256 boundary snaps full-scale. Measured on a window that actually contains a colony — object 24 of d000466_280_003, the largest in that image at 9,182 px, centred at (1783.2, 342.7):

  crop_store_rgb(store, "rgb", 1783.158135, 342.748203, 256, mtime)
  source window        19061 .. 38171 uint16   (74.6 wraps of the 256 cycle)
  rendered PNG         193 KB
  mean neighbour delta 85.3            smooth imagery reads 0-5
  deltas > 100         36.8% of pixels
todaymod-256 truncation
scaledper-image range, cached
compositedobjmap boundary, label 24

The store is not affected. On disk the data is uint16, 5,799 distinct values in one 256×256×3 window, not multiples of 256 or 257 — genuine 16-bit acquisition data, untouched. The loss happens in RAM, in the render path, after the read. Viv-backed surfaces read the same chunks and apply contrast client-side, which is why Plate and Colony look right and only the PNG crop route does not.

Bug 2 · the obvious fix introduces a second bug

The same function already imports _normalize_to_uint8, whose docstring says it exists for this case — "Integer dtypes are rescaled by their global max so that e.g. uint16 RGB lands in 0..255". The rgb branch simply returns before reaching it. But that helper min–max stretches the array it is handed, which for a crop is that crop's own 256 px window:

  window A: source 18315..31783   a true 24000 renders as 107.6
  window B: source 20539..28559   a true 24000 renders as 110.0
  window C: source 20445..27877   a true 24000 renders as 122.0

Same physical brightness, three renderings. For a gallery whose job is comparing colonies side by side, that is its own defect.

The fix · a stable per-image scale, derived once and cached

Scale rather than cast, against a range computed from the image — not from the crop window — and cached on (store path, mtime_ns), the key crop_store_rgb already takes.

_shared/tiles.py — _store_layer_array_to_rgb
  - if layer == "rgb":
  -     return arr.astype(np.uint8)          # mod-256 truncation
  + if layer == "rgb":
  +     lo, hi = image_display_range(store, mtime_ns)
  +     return scale_to_uint8(arr, lo, hi)   # scale, then clip

Where the range comes from — measured, not guessed. Reading the whole smallest pyramid level costs almost nothing: rgb/4 is 374 KB and reads in 39 ms. Subsampling rgb/0 by 8 takes 79 ms. Use min/max, not a percentile: a 0.5/99.5 percentile on rgb/4 gives 21,644–25,993 against a true range of 17,912–45,344, which would clip the colonies — the brightest thing in the frame and the entire point of the picture. Clip on apply instead; a few saturated pixels beat 52 sawtooth wraps.

Measured on the same colony crop, scaling against rgb/4's range of 20,511–44,047:

  mean neighbour delta   85.3  ->  7.2
  deltas > 100          36.8%  ->  0.0%
  PNG size              193 KB -> 128 KB   noise does not compress
  colony vs background    n/a  ->  90 vs 32 (mean, 0-255)

Honest caveat on the default: 90-against-32 is correct but dim. The top of the per-image range is set by a specular highlight rather than by any colony, so most of the 0–255 budget sits above the subject. It is readable and it is safe — nothing clips — but contrast polish (a gentle gamma, or a smarter upper bound) is a follow-on, not part of the correctness fix.

Regression test: a synthetic uint16 store holding a monotonically increasing ramp must render monotonically non-decreasing. That invariant is exactly what the truncation violates and what any correct scaling satisfies, so the test fails if the bug is ever reintroduced.

Known limitation, stated rather than hidden: a per-image scale still means two different images can map differently, and prev/next in the inspector steps across images. A run-level scale fixes it and is v2; per-image is correct within a plate and is what every crop consumer needs today.

Option 2 · composite the contours server-side

The store path served no contours at all — layer=rgb is bare pixels and layer=objmap is a colourised label map with no plate underneath. Only the overlay-PNG fallback had contours, and that path is dead whenever a store exists. So "overlay by default" needs the composite to be built.

It is nearly free: rgb/labels/objmap/0 is 0.0 MB on disk for the entire level. Read the objmap window alongside the rgb window, take boundaries with skimage.segmentation.find_boundaries (skimage 0.25.2 is already a dependency), tint the focal Object_Label in one colour and its neighbours in a muted one, and encode. Measured on object 24: 330 boundary pixels, 0.50% of the crop, and the composited PNG is 129 KB against 128 KB uncomposited — the contour costs 1 KB.

A flag, not a new layer. LayerName = Literal["rgb", "detect_mat", "objmap"] names store series; "overlay" is a render mode. Adding it as a fourth member would conflate the two and break the get_args(LayerName) validation at the route boundary. It becomes a separate ?contours= parameter instead.

Resolve the label path from attributes.phenotypic.labels — {"objmap": "rgb/labels/objmap"} in this store — never hard-coded, per the rule in CLAUDE.md.

10

Two spikes, before any layout code

Both are cheap, both are measurements rather than opinions, and both change the design if they come back wrong.

Spike A · how many gl subplots survive in one figure

Build a make_subplots figure of N panels, each a go.Scattergl trace, and raise N until the browser drops contexts. The repo already renders gl traces inside a 3-panel make_subplots figure (_measure_orientation_zones.py:2190, traces at :2528), so 3 is known good and 16 is the number in question. Output: the value of SCATTER_FACET_CAP, and whether the single-axes fallback is needed.

Spike B · does kaleido export a gl layer headless

Render one Maresca section to PDF through kaleido on a compute node. Output: points present or absent, and raster or vector. Absent reopens Q2; raster is a note in the docs unless you need vector artwork.

Executing the grouping design broke it — get_headers() is not uniformly zero-argument

The design said: instantiate each measurer from pipeline.json["meas"], call get_measurement_infoclasses(), then get_headers(). Run against this store, that throws:

  TEXTURE.get_headers() missing 1 required positional argument: 'scale'

TEXTURE.get_headers(cls, scale, matrix_name=None) (schema/_texture.py:160) is parameterized, because its columns carry the offset — Texture_Contrast-deg000-scale05. Every other schema in this run is zero-arg. Naively, that dumps all 65 Texture columns into Unattributed — 44% of the frame in the fallback bucket, and an inspector that is simply wrong.

Resolution: try get_headers(); on TypeError, match the frame's columns against info.category() and mark the group as resolved by category rather than by exact headers. Total, no core change, and it covers any future parameterized schema. The deliverables README generator does not hit this because it documents members, not headers — so it never validated the approach.

A zero-argument MeasureFeatures.emitted_headers() on the ABC would make this exact rather than heuristic. That is a core change and belongs in its own proposal, not this one.
