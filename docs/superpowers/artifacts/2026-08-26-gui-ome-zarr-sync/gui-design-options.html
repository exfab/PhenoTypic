Cut three surfaces, then rebuild the viewer on Viv

The results viewer stops producing pyramids and starts consuming them. Every decision below follows from one shift: with Viv/vizarr the browser reads zarr chunks directly over HTTP range requests, so the server does no tiling at all — a deletion, not an optimization.

One consequence worth naming now

Unmounting QC and Error takes the curation radial menu with them unless it is deliberately kept on the Colony tab. Curation is the only thing in the viewer that writes — deliverables/errors/<category>.parquet and the durable qc/curation_labels.parquet. If the radial goes dark, the GUI becomes read-only and the CLI's reemit_error_deliverables round-trip has no producer. I need a call on this (see asks).

Where pixels come from today

Four independent paths. Three of them build a pyramid the zarr store will already contain.

SurfacePathPeak costAfter zarr
Browse source image → libvips DZI → revision-keyed BrowseCache → OSD 8–10 GiB LRU on disk unchanged no run, no store
Results plate _load_hdf_layer_rgb reads the whole layer → PNG → _dzi_tiler writes DZI files to .viewer_cache/ → OSD full raster resident + a duplicated on-disk pyramid deleted browser reads chunks
Builder preview HDF layer → PNG → _dzi_tiler → DZI same, per preview node decision E
Colony tiles decode the entire deliverables/overlays/<ds>/<stem>.png, LRU it, slice 64² crops whole overlay resident to serve a thumbnail deleted chunk read at L0

The size of the prize

A 4000×3000 plate at --pyramid-levels auto is 4 levels (the spec's ceil(log2(max(H,W)/512))+1), smallest level 500×375. Today the viewer recomputes exactly that pyramid into .viewer_cache/ after materializing the full raster. Post-change the plate tab's server work is: serve bytes. No decode, no resize, no cache directory, no _dzi_tiler at all on this path.

Feasibility check — what I verified, what I didn't

web-verified 2026-08-26 · anything marked UNVERIFIED needs a spike before it enters the spec as fact

Sharding in the browser

verified

zarrita.js supports Zarr v3 with ZEP2 sharding, natively in browsers, zero dependencies. The backend's (C, 4096, 4096) shards over (1,1024,1024) chunks are readable client-side.

sourcezarrita.dev · github.com/manzt/zarrita.js

zstd in the browser

conditional

Not in zarrita's built-in registry. It requires registering the numcodecs.js wasm zstd codec via zarr.registry.set() before the first read. Workable — but it is an extra wasm payload and an initialization ordering hazard, and it is the kind of thing that fails only in production.

bears onDecision C

Viv & vizarr licensing

verified

Both MIT. Compatible with PhenoTypic's Apache-2.0. Adapting the source is fine; it needs a NOTICE entry plus licenses/viv-MIT.txt and licenses/vizarr-MIT.txt, matching the existing pattern for SAM2 / micro-sam / filfinder.

sourcehms-dbmi/viv · BioNGFF/vizarr

bioformats2raw.layout series

unverified

The store is a named-series collection (rgb/gray/detect_mat + a labels/objmap child). vizarr reads bioformats2raw layouts, but whether it resolves our series list and label child without patching is untested. This is the most likely place the "adapt vizarr" plan meets friction.

No JS toolchain exists here

blocking

There is no package.json anywhere in the repo. Every line of GUI JS is either hand-written vanilla (builder.js, browse.js) or a vendored pre-built bundle (openseadragon.min.js, cytoscape-dagre.min.js) dropped into a Dash _assets/ folder. Viv is React + deck.gl; vizarr is Preact + Vite. Neither can be dropped in as a file. This is Decision A and everything else waits on it.

The backend doesn't exist yet

sequencing

worktree-ome-zarr-image-store is three doc commits — no zarr code in src/. This GUI spec is written against a contract, and the plan can't execute until that contract is code. Good news: it forces the spec to name exactly which clauses of §1–§4 it depends on.

Decision A — how does Viv get into a Dash app?

The hinge decision. Dash is React, so a real component is possible — but it means owning a JS build in a repo that has never had one.

Option A1 · recommended

Vendored pre-built bundle + imperative façade

Build Viv+deck.gl into one IIFE bundle outside the repo, commit the artifact next to openseadragon.min.js, and drive it from a hand-written viv_viewer.js that exposes mount/setSource/setViewState/destroy. Dash clientside callbacks talk to that façade.

  • Zero new toolchain in CI, in the wheel, in contributor setup.
  • Exactly the pattern the repo already uses twice — reviewers know how to read it.
  • Python stays the only thing tests need.
  • Bundle provenance lives outside the repo — needs a committed, reproducible build recipe or it rots.
  • Upgrading Viv is a manual ceremony, not npm update.
  • Bundle size: deck.gl + Viv is not small (~1 MB class). Fine on localhost/SSH-tunnel, which is the whole deployment story.
Option A2

Real JS build in-repo (npm + Vite)

Add package.json, build the viewer bundle at package time, ship the output in the wheel.

  • Honest dependency graph; upgrades and audits are ordinary.
  • Makes future component work cheap instead of one-off.
  • New CI job, new contributor prerequisite, new wheel-build step in a project whose entire toolchain is uv.
  • Sdist/wheel reproducibility gets materially harder — node in the build path.
  • Biggest cost of the four, and it buys nothing the first release needs.
Option A3

iframe a stock vizarr + postMessage

Ship vizarr's published build untouched, mount it in an iframe, bridge selection/viewport over postMessage.

  • Fastest thing that shows a plate on screen — days, not weeks.
  • Upstream stays upstream; no fork to maintain.
  • Kills Decision D. The colony grid needs custom deck.gl views; an iframe gives you vizarr's UI, not your own.
  • Curation overlays, radial menus, and tile chrome can't live inside someone else's canvas.
  • Another URL-prefix surface to get right behind Open OnDemand's path-stripping proxy.
Option A4

Proper Dash custom React component

The official dash-component-boilerplate route: a published component package wrapping Viv.

  • The "correct" answer in the abstract; cleanest prop/state story.
  • A2's toolchain cost plus a second distributable to version, publish, and pin.
  • Dash component builds are notoriously brittle to React-version drift — Viv pins its own.
  • Wildly out of proportion to one viewer in one internal tool.
my read

A1, with the build recipe committed as a script + pinned lockfile under tools/viv-bundle/ so the artifact is reproducible even though the build isn't run in CI. It preserves the "adapt Viv as much as possible" goal — you're adapting Viv's layers, which is where the value is — while keeping uv the only thing a contributor installs. Take A2 instead if you expect more custom JS surfaces within a year; the toolchain amortizes then.

Decision B — how do zarr bytes reach the browser?

Option B1 · recommended

Range-capable static route under the results blueprint

A /zarr/<dataset>/<stem>.ome.zarr/<path> Flask route using send_file(..., conditional=True), reusing the existing is_safe_path_component traversal guard.

  • Sharding needs HTTP Range — a shard read is an index fetch plus a byte-range fetch. conditional=True gives it.
  • Server does no decode. Memory per request is a sendfile buffer.
  • Same guard, same blueprint conventions as _tile_routes.py today.
  • Path-traversal surface is wider than the old route (arbitrary depth inside a store) — the guard must be per-segment, not per-URL.
Option B2

Explicit chunk API that reads through zarr-python

Server opens the store, slices, returns a typed-array response the client assembles.

  • Server controls exactly what's exposed; no raw store on the wire.
  • Codec problems vanish — server decodes, so Decision C stops mattering.
  • Reintroduces per-request decode — the exact cost this whole change exists to delete.
  • Viv/zarrita would need a custom store adapter; you'd be fighting the library.
Option B3

Keep serving PNG tiles from zarr levels

Read the right pyramid level server-side, emit PNG tiles, keep OSD.

  • Smallest diff. No JS decisions at all. A genuine fallback if A and C both go badly.
  • No Viv, no deck.gl, so no Decision D — the colony grid stays DOM <img> tiles.
  • Still decodes and re-encodes on every request. Keeps the redundancy, just relocates it.

Decision C — codec & chunk shape amends the backend spec

The backend spec locks zstd and (1,1024,1024) chunks (§1.4) — chosen for write throughput on Lustre, with no browser reader in the picture. A client-side viewer changes the constraints that decision was made under, so it is fair to reopen it — but it must be reopened there, as a recorded amendment, not quietly worked around here.

Option C1 · recommended

Keep zstd, ship the wasm codec

Register numcodecs.js's zstd in the bundle's startup path before any store is opened.

  • Backend spec untouched. No amendment, no re-review of a decision that has good write-side reasons.
  • zstd genuinely is the better stored format — smaller and faster to decompress than gzip-4.
  • Adds a wasm payload and a hard initialization ordering rule: register before first read or every read fails.
  • Needs a real test that a store written by the CLI opens in a browser — not just that the codec registers.
Option C2

Amend §1.4 to gzip for browser-friendliness

Trade stored size and write speed for a codec every JS reader has built in.

  • Removes the wasm dependency and the ordering hazard entirely.
  • Reverses a locked decision to make the client simpler, penalizing every CLI write forever.
  • The spec explicitly moved off gzip-4. Undoing it needs a better reason than "less JS setup".
Option C3

Revisit chunk size for viewing (1024² → 512²)

Independent of codec: a deck.gl tile fetch pulls a whole inner chunk. At 1024²×3×u8 that's ~3 MB per tile.

  • 512² quarters the bytes-per-tile and smooths panning noticeably.
  • Quadruples chunk count; the spec's file-count table (16/40/132 files) all shifts.
  • I have not measured this. It may be a non-issue over localhost or an SSH tunnel — which is the only deployment. Do not spec it without a number.
the honest version

C1 and C3 are independent, and C3 is the one I'd refuse to decide without measuring. Panning latency over an SSH tunnel at 3 MB/tile is an empirical question with a cheap answer, and guessing it into a spec is how a plausible number becomes a load-bearing one nobody rechecks.

Decision D — the colony grid, as a port of _smart_grid

What gui/_smart_grid/ actually does: patch napari's viewer.grid so only visible layers get cells, then create_overlay_clones duplicates every Labels/Points/Shapes visual into each viewbox — so every cell shows a different base image under the same annotation, sharing one camera. Below: three ways to say that in deck.gl.

Option D1 · recommended · closest port

N deck.gl views, one shared view state

One OrthographicView per colony, each with its own viewState centred on that colony's centroid; the Viv layer stack renders into all of them. Zoom/pan edits one shared value applied to every view.

  • Shared camera is free — it's one viewState, not a sync protocol.
  • Per-cell chrome (label, curation badge) is a deck.gl overlay in that view's own coordinates.
  • The "only visible layers get cells" rule ports directly as view-list construction.
  • deck.gl re-renders every view each frame; with hundreds of cells that needs a virtualization cap.
Option D2

One view, colonies montaged into a virtual canvas

A single camera over a synthetic layout where each colony is drawn at an offset — the grid is a coordinate transform, not a set of viewports.

  • Scales to thousands of cells without virtualization.
  • Selection/box-drag across cells is trivial — one coordinate space.
  • Per-cell independent zoom is impossible by construction.
  • Multiscale level selection gets muddy: one camera zoom, many source regions.
Option D3

Keep the DOM tile grid, re-source it

Today's build_tile_grid chrome stays; only the crop route changes from overlay-PNG slicing to a zarr L0 chunk read.

  • Curation radial, multi-select, shift-click ranges, bulk-mark all keep working unchanged.
  • Smallest risk by a wide margin, and it still deletes the full-overlay-decode.
  • Not a Viv port at all — no shared camera, no live layer toggling, no deck.gl.
  • Server stays in the pixel path for colony tiles.
sequencing note

D3 is a valid first release and D1 a valid second — they differ in the rendering layer, not the data path, and both need the same zarr crop reader underneath. If you want something usable early, that ordering gets it without wasted work.

Decision E — builder preview has no store to read

Easy to miss: the builder previews a pipeline against an input image. There is no run, so there is no .ome.zarr and no pyramid. "Optimize preview with zarr" needs a source of zarr first.

Option E1 · recommended

Preview writes an ephemeral store

Each preview node writes its layer to a scratch .ome.zarr under the existing builder-tiles sandbox dir, reusing the CLI's writer. The viewer then reads it exactly like a real run.

  • One reader, one code path for every viewing surface in the GUI.
  • Exercises the writer constantly during development — bugs surface in the builder, not on a cluster.
  • Preview gets a write cost it doesn't have today, and a scratch dir to garbage-collect.
  • Pyramiding a preview is mostly wasted work at preview resolutions.
Option E2

Leave the builder on PNG→DZI

Scope the change to the results viewer; the builder keeps _dzi_tiler.

  • Smallest scope. The preview cache's PNG-bytes design (~10–15 MB vs 1–2 GB) is already deliberate and working.
  • _dzi_tiler survives for one consumer — the redundancy shrinks but doesn't die.
  • Two viewer stacks to maintain in one app.
Option E3

In-memory zarr store served from the process

Keep the preview array in RAM behind a store-shaped route; never touch disk.

  • No scratch files, no GC, no cleanup on crash.
  • Preview images are small; RAM is the right medium for them.
  • A hand-written store endpoint is a third pixel path, not a unification.
  • Doesn't survive the multi-worker deployment the run console already assumes.
