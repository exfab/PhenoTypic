1. Intent

#281 changed the CLI's contract in ways the GUI still reads the old way. It also deliberately made no change under src/phenotypic/_gui/ (its spec, §2.2). #282 added a GPU Stage 4 for embeddings that the GUI cannot reach.

PR A makes the GUI read #281's contract:

  • exit codes 3 and 4;
  • per-pipeline table folders;
  • TSV;
  • the *.pht-*.json suffixes.

It also:

  • turns the 13 GUI tests #281 left red back to green;
  • retires measurements.csv, which means a CLI change (D1);
  • lets a run that finished with failed images be curated (D2);
  • lets every metadata picker take a .tsv (D8).

PR B lets the run console reach Stage 4:

  • an --embed-stage control;
  • a GPU section shown whenever the CLI would use it;
  • Stage-4 refusals shown the way the staged-GPU refusal already is;
  • --mode measure (D6).

Sequencing (D5).

  1. Now. PR A is built on #281's branch.
  2. #281 merges to main first. PR A targets main after that.
  3. Before PR A is opened:
    • git fetch origin and rebase feat/gui-dvc-followups onto the latest origin/main, which will by then contain #281;
    • re-verify every PR A citation in this spec against the rebased tree. Line numbers will move. A cited behaviour that changed is a spec change, not a plan detail.
  4. PR B is cut only after #282 has been rebased or merged onto a main that contains PR A. PR B needs PA1, because a Stage-4 SLURM submission exits 4 like any other, and it needs PA4's status helper (PB5).

This reverses #281's own merge gate ("#281 does not merge to main before #283 fixes these", #281 spec §2.2). Between the two merges main carries the breaks in §3. See §7 R9 and §11 Q1.

2. Goals, non-goals, anti-goals

2.1 Goals

  • G1. A SLURM launch the CLI queued is shown as queued, in every case.

    • No queued run reads as failed.
    • The GUI never cancels a generation because the submitter exited 4.

  • G2. A run that exits 3 (COMPLETE_WITH_FAILURES) reads "complete, N images failed" wherever the GUI states a run's outcome:

    • Recent Runs;
    • the run banner;
    • the results-viewer and analysis snapshot badge (D3).

    It reads the same whether the run was local or SLURM.

  • G2b (D2). Such a run can be curated. Its failed images have no rows, and curating it leaves every enforced run-proof descriptor valid.

  • G3. The Colony picker and the measurement routes read a v2 store's latest measuring run, tables/<n>-<sha12>/measurements/table.parquet, and still read a v1 store.

  • G4. The 13 expected-red tests (#282 plan README) are green, through the fix each one needs. No xfail and no skip.

  • G5. Every tabular text file PhenoTypic writes for the mirror or the GUI is TSV:

    • measurements.csv is no longer written (D1);
    • every reader prefers .tsv and falls back to .csv in an older tree;
    • an older tree's generated measurements.csv is retired after the TSV is published.

  • G5b (D8). Every metadata picker and table reader in the GUI accepts .tsv wherever the CLI does.

  • G6. Every GUI surface that lists, filters, loads or writes a typed config agrees with the sdk_ suffix sets:

    • the new .pht-*.json names are written;
    • the old .json.pht-* names are still read;
    • a tune spec is never listed as a pipeline.

  • G7 (PR B). A pipeline that can run Stage 4 can be launched with Stage 4 from the GUI, with the same resolution the CLI applies, in full and measure mode.

  • G8 (PR B). Every Stage-4 refusal the GUI can know before launch is shown in rc-staged-gpu-refusal, with Run disabled. The text is the CLI's own message.

  • G9. FEATURES.md, WORKFLOWS.md, the tutorial text and the tutorial screenshots match the shipped chrome.

2.2 Non-goals

  • The follow-up issue (§8), drafted here, not opened:
    • the results-viewer run picker;
    • the DVC dvc commit hint;
    • an embeddings view.
  • Tune runs' exit codes. phenotypic.tune does not use RunExitCode at #281: there is no reference under src/phenotypic/tune/, and its exits are SystemExit(message) at tune/__main__.py:236 and tune/_tune_cli/_worker.py:97,102. The tune monitor's reap logic (_gui/tune/_callbacks.py:741-745) is therefore unchanged.
  • Claiming a CLI-launched run that has failures, for --retry-failures. It stays refused (D2). The refusal is _foreign_run_conflict, shell/_runs_registry.py:1407-1480.
  • --mode recompile, process and migrate in the run console. PR B adds measure only (D6).
  • Changing resolve_run_state's Completion literals, or the CLI's exit codes.
  • A tutorial screenshot of the new status (D4). It is documented in tutorial text instead.

2.3 Anti-goals (failure even if everything "works")

  • A queued SLURM run shown as failed, or a submission's generation cancelled by the GUI.
  • A run shown as complete when an accepted image has neither a success nor a terminal-failure record.
  • A curation write that makes an enforced proof descriptor (master, metrics.json, schema.json) stop matching, or that changes the run's verdict.
  • A curated measurements.tsv that disagrees with measurements.parquet after a curation write that reported success.
  • A GUI-side copy of a CLI decision rule (Stage-4 resolution, a refusal condition, the "finished with failures" verdict, measure's argument rules) that can drift from the CLI's.
  • A test made green by deleting or weakening the property it pins.
  • A legacy .json.pht-* config, or a legacy measurements.csv tree, that the GUI used to open and no longer can.
  • An argv the GUI builds that the CLI refuses as a usage error.

3. What the code does today (verified)

3.1 Exit code 4 does not fail every SLURM launch. Its effect is narrower, and worse

#283 says _slurm.py:826 "treats any non-zero exit as a failed submission". That is true of the branch at :826, but not of the outcome. Every non-zero exit sets ambiguous_error (run_console/_slurm.py:826-831), and submit_slurm then runs the recovery path that was built for timeouts: _reconcile_submission (:642-743, called at :837-841).

I probed submit_slurm at 36b9e840e with the submitter mocked:

Case Submitter exit Result
Legacy chunk_job_ids manifest 4 SlurmSubmitResult, reconciled=True
Lifecycle active, job ledgered 4 SlurmSubmitResult, reconciled=True
Lifecycle inactive 4 cancel_generation called, then SlurmSubmitError("…exited with code 4")
No job recorded 4 SlurmSubmitError("…exited with code 4")
Nothing submitted (all done) 3 SlurmSubmitError("…exited with code 3")
Nothing submitted (all done) 0 SlurmSubmitError("…exited cleanly but … contain no submitted jobs")

What that means in practice:

  • The ordinary case reaches queued. But every submission is now labelled reconciled, which erases the signal that something went wrong.
  • If the scheduler evidence is slow to land, a queued run reads failed. The registry takes status="failed" from the except Exception arm at run_console/_callbacks.py:1086-1114.
  • If the fence reads inactive, the GUI cancels its own generation. The branch is _slurm.py:652-656.
  • A SLURM-mode run with nothing left to do never submits, and exits 0 or 3. Today it either fails or binds to the previous generation's job set:
    • The exits come from phenotypicCLI.py:3897-3899, :3964 and :4165-4225. The code at :4165 reads if results.submitted: … sys.exit(RunExitCode.SUBMITTED), and otherwise the run finished in-process.
    • The stale binding is in read_submitted_job_set. With no expected_generation (_slurm.py:372-432), _generation_for (:234-261) prefers the lifecycle on disk.
    • The exit-0 half predates #281. The exit-3 half is new: the earlier run's fence is inactive, so the same branch calls cancel_generation on that finished generation.

3.2 "Complete with failures" has no representation anywhere in the GUI

  • Local. observe_local_exit maps every non-zero exit to failed (shell/_runs_registry.py:661-663).
  • SLURM. A run with any terminal failure never gets a run proof. publish_run_completion_evidence raises unless every accepted image succeeded (_cli/_cli_completion.py:1304-1342). The observer therefore reaches the "inactive, no marker" branch and reports failed, with "lifecycle ended terminal-incomplete without a current run-completion marker" (run_console/_slurm_observer.py:661-671).
  • Boot rehydration. resolve_run_state(...).completion is "failed" for such a run (sdk_/_run_state.py:1922-1934), and _rehydrated_status passes it through (shell/_runs_registry.py:1026-1104).
  • The viewer and analysis snapshot badge reads "Run failed" (_gui/_snapshot_status.py:47-50).
  • Curation is refused. Every write-authority check asks completion == "complete":
    • _mutation_guard.py:38-45, used at :121, 140, 170, 216;
    • OutputRoot.run_is_complete, _output_root.py:700-713;
    • mutation_snapshot_is_safe, :780-797;
    • the processing-inventory reuse rule, _processing_inventory.py:97. Only a reusable inventory is "exhaustive" (:130-145), and the guard refuses a non-exhaustive one (_mutation_guard.py:127-131).

phenotypic-wait already decides "complete with failures" from disk, in decide_wait_outcome (_cli/_cli_wait.py:309-366), rule 3: completion failed, no unresolved image, and published. Its seams are:

  • _run_snapshot (:116-130);
  • _published (:182-242);
  • _cancelled (:245-266);
  • _generation_failures (:269-285);
  • _is_process_run (:288-301).

Two aggregate-proof checks disagree about the curated mirror, and that matters for D2:

  • valid_aggregate_snapshot (_cli/_cli_completion.py:1271-1301) hashes every required_outputs descriptor, so it returns None after any curation write.
  • aggregate_proof_is_current (sdk_/_run_state.py:1415-1433, exported) skips the GUI-written descriptors in _GUI_WRITTEN_PROOF_DESCRIPTORS (:1331-1333, checked at :1369-1371).

PA4. Exit 3 reads "complete, N images failed"

Behaviour. A run whose every accepted image is resolved, with at least one terminal failure and its deliverables published, gets the terminal registry status complete_with_failures and a count failed_images = N. N is the run state's diagnostics.failed, the count the CLI's exit code uses (phenotypicCLI.py:1493-1518).

It is shown in four places:

  • Recent Runs: complete · N failed.
  • The status banner (update_log_tail, run_console/_callbacks.py:2581-2622): the same text.

The rule. One predicate, run_permits_mutation(state, output_dir), is true for a bundle (state is None), for completion == "complete", and for a confirmed COMPLETE_WITH_FAILURES. It replaces every completion == "complete" write-authority check:

  1. The verdict, fresh, at all three points. At bind, on the fresh deep state, and on the verified deep state, run_permits_mutation must hold. Any change, such as a retry that repaired an image or a new failure, refuses the write.
  2. The run identity digest is unchanged across the three (:146-150, 169-177).
  3. No active owner (:151-154, 172) and a current processing snapshot (:155-159).
  4. The failed count N is part of the verdict. A write authorized against "N failed" is refused if the fresh verdict says otherwise. [call] The receipt records N beside the identity digest, so a test can assert it.
