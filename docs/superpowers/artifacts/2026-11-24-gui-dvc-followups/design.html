1. Intent

#281 changed the CLI's contract in ways the GUI still reads the old way. It also deliberately made no change under src/phenotypic/_gui/ (its spec, §2.2). #282 added a GPU Stage 4 for embeddings that the GUI cannot reach.

PR A makes the GUI read #281's contract:

  • exit codes 3 and 4;
  • per-pipeline table folders;
  • TSV;
  • the *.pht-*.json suffixes.

It also:

  • turns the 13 GUI tests #281 left red back to green;
  • retires measurements.csv, which means a CLI change (D1);
  • lets a run that finished with failed images be curated (D2) and relaunched from the GUI, whoever launched it (D10);
  • lets every metadata picker take a .tsv (D8).

PR B lets the run console reach Stage 4:

  • an --embed-stage control;
  • a GPU section shown whenever the CLI would use it;
  • Stage-4 refusals shown the way the staged-GPU refusal already is;
  • --mode measure (D6).

Sequencing (D5, D9).

  1. Now. PR A is built on #281's branch.
  2. #281 is held until PR A is reviewed and ready (D9), then merges to main. PR A targets main and merges right after it.
  3. Before PR A is opened:
    • git fetch origin and rebase feat/gui-dvc-followups onto the latest origin/main, which will by then contain #281;
    • re-verify every PR A citation in this spec against the rebased tree. Line numbers will move. A cited behaviour that changed is a spec change, not a plan detail.
  4. #282 is rebased or merged onto a main that contains PR A. That is #282's obligation, and it includes one real conflict (I2, R13):
    • #282 rewrites _cli/_cli_wait.py: _published gains the U16 terminal_status override (0993c8e06 _cli_wait.py:204-279, override at :228-257), _ledgered_jobs is added (:182-195), and wait_for_run gains a frozen-outcome drain (:506+).
    • PA4 makes decide_wait_outcome compose the new sdk_ verdict, and adds the generation-bound wrapper the SLURM observer uses.

  5. PR B is cut only after step 4. PR B needs PA1, because a Stage-4 SLURM submission exits 4 like any other, and it needs PA4's verdict (PB5).

2. Goals, non-goals, anti-goals

2.1 Goals

  • G1. A SLURM launch the CLI queued is shown as queued, in every case.

    • No queued run reads as failed.
    • The GUI never cancels a generation because the submitter exited 4 or 2.

  • G2. A run that exits 3 (COMPLETE_WITH_FAILURES) reads "complete, N images failed" wherever the GUI states a run's outcome:

    • Recent Runs;
    • the run banner;
    • the results-viewer and analysis snapshot badge (D3).

    It reads the same whether the run was local or SLURM. It is shown only while the run's aggregate publication still covers the run as it now stands (C1), or, when every image failed, while none exists (D16).

  • G2b (D2, D10). Such a run can be curated, and relaunched from the GUI for Run, --retry-failures, Validate and Measure, whoever launched it. Its failed images have no rows, and curating it leaves every enforced run-proof descriptor valid.

  • G3. The Colony picker and the measurement routes read a v2 store's latest measuring run, tables/<n>-<sha12>/measurements/table.parquet, and still read a v1 store.

  • G4. The 13 expected-red tests (#282 plan README) are green, through the fix each one needs. No xfail and no skip.

  • G5. Every tabular text file PhenoTypic writes for the mirror or the GUI is TSV:

    • measurements.csv is no longer written (D1);
    • every reader prefers .tsv and falls back to .csv in an older tree;
    • an older tree's generated measurements.csv is retired after the TSV is published;
    • error_analysis.csv stays CSV for now (D18; §8).

  • G5b (D8). Every metadata picker and table reader in the GUI accepts .tsv wherever the CLI does.

  • G6. Every mounted GUI surface that lists, filters, loads or writes a typed config agrees with the sdk_ suffix sets:

    • the new .pht-*.json names are written;
    • the old .json.pht-* names are still read;
    • a tune spec is never listed as a pipeline.

  • G7 (PR B). A pipeline that can run Stage 4 can be launched with Stage 4 from the GUI, with the same resolution the CLI applies, in full and measure mode.

  • G8 (PR B). Every Stage-4 refusal the GUI can know before launch is shown in rc-staged-gpu-refusal, with Run disabled. The text is the CLI's own message.

  • G9. FEATURES.md, WORKFLOWS.md, the tutorial text and the tutorial screenshots match the shipped chrome.

2.2 Non-goals

  • The follow-up issue (§8), drafted here, not opened:
    • the results-viewer run picker;
    • the DVC dvc commit hint;
    • an embeddings view;
    • the unmounted tune app's suffix surfaces.
  • Tune runs' exit codes. phenotypic.tune does not use RunExitCode at #281: there is no reference under src/phenotypic/tune/, and its exits are SystemExit(message) at tune/__main__.py:236 and tune/_tune_cli/_worker.py:97,102. The tune monitor's reap logic (_gui/tune/_callbacks.py:741-745) is therefore unchanged.
  • Unmounted chrome. The hub does not compose _gui/tune/, so /tune/ 404s (_gui/CLAUDE.md:20-26). PR A changes tune code only where:
    • a red test needs it (#1–6);
    • the user named the site (D8's tune pickers).
  • Reapplying curation in the CLI's finalize (D11). A CLI re-run of a run with failures reseeds the mirror without curation labels; see PA10.
  • Claiming an unfinished or live run from the GUI. It stays refused (PA11).
  • --mode recompile, process and migrate in the run console. PR B adds measure only (D6).
  • Changing resolve_run_state's Completion literals, or the CLI's exit codes.
  • A tutorial screenshot of the new status (D4). It is documented in text instead.
  • Editing anything outside the repository (D12).

2.3 Anti-goals (failure even if everything "works")

  • A queued SLURM run shown as failed, or a submission's generation cancelled by the GUI.
  • A run shown as complete, or made writable, when:
    • an accepted image has neither a success nor a terminal-failure record; or
    • its aggregate publication no longer covers the run's inventory, configuration, metadata or verified set (C1).
  • A curation write that makes an enforced proof descriptor (master, metrics.json, schema.json) stop matching, or that changes the run's verdict.
  • A curated measurements.tsv that disagrees with measurements.parquet after a curation write that reported success, or a stale text mirror a reader can fall back to.
  • A persisted non-terminal status that no process will ever move, which locks the output.
  • A GUI-side copy of a CLI decision rule (Stage-4 resolution, a refusal condition, the "finished with failures" verdict, measure's argument rules) that can drift from the CLI's.
  • A test made green by deleting or weakening the property it pins.
  • A legacy .json.pht-* config, or a legacy measurements.csv tree, that the GUI used to open and no longer can.
  • An argv the GUI builds that the CLI refuses as a usage error, or one carrying a flag the user cannot see.

3. What the code does today (verified)

3.1 Exit code 4 does not fail every SLURM launch. Its effect is narrower, and worse

#283 says _slurm.py:826 "treats any non-zero exit as a failed submission". That is true of the branch at :826, but not of the outcome. Every non-zero exit sets ambiguous_error (run_console/_slurm.py:826-831), and submit_slurm then runs the recovery path that was built for timeouts: _reconcile_submission (:642-743, called at :837-841).

I probed submit_slurm at 36b9e840e with the submitter mocked:

Case Submitter exit Result
Legacy chunk_job_ids manifest 4 SlurmSubmitResult, reconciled=True
Lifecycle active, job ledgered 4 SlurmSubmitResult, reconciled=True
Lifecycle inactive 4 cancel_generation called, then SlurmSubmitError("…exited with code 4")
No job recorded 4 SlurmSubmitError("…exited with code 4")
Nothing submitted (all done) 3 SlurmSubmitError("…exited with code 3")
Nothing submitted (all done) 0 SlurmSubmitError("…exited cleanly but … contain no submitted jobs")

What that means in practice:

  • The ordinary case reaches queued. But every submission is now labelled reconciled (reconciled=ambiguous_error is not None, :871), which erases the signal that something went wrong.
  • If the scheduler evidence is slow to land, a queued run reads failed. The registry takes status="failed" from the except Exception arm at run_console/_callbacks.py:1086-1114.
  • If the fence reads inactive, the GUI cancels its own generation. The branch is _slurm.py:652-656, and _reconcile_submission reaches it from every caller, the clean exit with no job set (:837-841) included.
  • Exit 2 also reconciles and can cancel. A usage error is raised in the CLI's read-only half, before anything is submitted, yet test_abnormal_exit_cancels_recovered_inactive_generation (tests/unit/gui/run_console/test_slurm.py:815-838) pins a cancel_generation call on a previous, inactive generation. A deactivated fence is never relabelled (_cli/_cli_slurm_lifecycle.py:700-704), so the effect is mostly harmless. But the cancel can scancel ids left without a terminal ledger row, and PR B adds more usage errors.
  • When a SLURM-mode re-run exits 0 or 3 without submitting (review C4):
    • A complete run with nothing left to do exits 0 (phenotypicCLI.py:3897-3899, :3964).
    • A run with failures and at least one verified image never takes that path. Its startup verdict is never complete, so publication_refresh_required is set (:3765-3790). With nothing left to process it goes to _handle_recompile_slurm (:3925-3944), which submits whenever a measurement source exists (:4672-4760) and exits 4.
    • Exit 3 without a submission comes only from:
      • a run with failures and no verified image, where nothing needs refreshing (:3964);
      • _handle_recompile_slurm's two local fallbacks (:4673-4688, :4700-4713), which run _handle_recompile inside the submitter process.
    • Today these exits either fail or bind to the previous generation's job set. The stale binding is in read_submitted_job_set: with no expected_generation (_slurm.py:372-432), _generation_for (:234-261) prefers the lifecycle on disk. The exit-0 half predates #281. The exit-3 half is new: the earlier run's fence is inactive, so the same branch calls cancel_generation on that finished generation.

3.2 "Complete with failures" has no representation anywhere in the GUI

  • Local. observe_local_exit maps every non-zero exit to failed (shell/_runs_registry.py:661-663).
  • SLURM. A run with any terminal failure never gets a run proof. publish_run_completion_evidence raises unless every accepted image succeeded (_cli/_cli_completion.py:1304-1342). The observer therefore reaches the "inactive, no marker" branch and reports failed, with "lifecycle ended terminal-incomplete without a current run-completion marker" (run_console/_slurm_observer.py:661-671).
    • A staged run with failures reaches that branch only because the finalizer closes its orchestration with the phase "terminal_incomplete" (_cli/_cli_checkpoint_handler.py:398-401).
    • That phase is absent from _STAGED_FAILURE_PHASES (_slurm_observer.py:92-94). Otherwise _staged_terminal_observation would return failed first (:642-649).
  • Boot rehydration. resolve_run_state(...).completion is "failed" for such a run (sdk_/_run_state.py:1922-1934), and _rehydrated_status passes it through (shell/_runs_registry.py:1026-1104).
  • The viewer and analysis snapshot badge reads "Run failed". The unfinished arm returns before the currency check (_gui/_snapshot_status.py:84-91 vs :92-98).
  • Curation is refused. Every write-authority check asks completion == "complete":
    • _mutation_guard.py:38-45, used at :121, 140, 170, 216;
    • OutputRoot.run_is_complete, _output_root.py:700-713;
    • mutation_snapshot_is_safe, :780-797;
    • the processing-inventory reuse rule, _processing_inventory.py:97. Only a reusable inventory is "exhaustive" (:130-145), and the guard refuses a non-exhaustive one (_mutation_guard.py:127-131).
  • Every relaunch is refused, whoever launched the run (review C2).
    • _assert_output_claimable_locked (shell/_runs_registry.py:1275-1300) lets a terminal owner record pass (:1288). It then calls _foreign_run_conflict(output_dir) unconditionally (:1298-1300).
    • That function never looks at the owner, and refuses completion == "failed" with "output has failed non-GUI processing state …" (:1469-1474).
    • allocate reaches the gate on every launch, Validate included (:412-413).
    • It is pinned by test_a_failed_image_refuses_the_claim (tests/unit/gui/shell/test_runs_registry.py:363-390).
  • A CLI re-run of such a run re-finalizes and reseeds the mirror (review C4).
    • The re-run reaches finalize through the refresh in §3.1.
    • Finalize reseeds measurements.{tsv,csv,parquet} from the post-applied master (_seed_measurements, _cli/_cli_output_manager.py:968-1003).
    • From curation_labels.parquet it re-emits only errors/ and error_analysis.* (_cli/_cli_error_outputs.py:56-65; "(no mirror)" at :63).
    • So a curated mirror returns to uncurated, while the labels file survives. A complete run's re-run is a no-op and keeps it.

What already decides "finished with failures". phenotypic-wait decides it from disk, in decide_wait_outcome (_cli/_cli_wait.py:309-366), rule 3: completion failed, no unresolved image, and published. Its seams are:

  • _run_snapshot (:116-130);
  • _published (:182-242);
  • _cancelled (:245-266);
  • _generation_failures (:269-285);
  • _is_process_run (:288-301).

Rule 3 never compares the aggregate proof to the run as it now stands.

The aggregate proof carries the digests rule 1 compares (_cli/_cli_completion.py:1244-1265): inventory_digest, finalization_input_digest, scientific_config_digest, source_set_digest and source_image_count.

For a complete run, _run_proof_covers_current_inventory (sdk_/_run_state.py:1464-1541) compares those against current state. Its docstring says why each comparison is load-bearing. A failed run has no run proof, so nothing makes those comparisons for it (C1).

Two aggregate-proof checks disagree about the curated mirror:

  • valid_aggregate_snapshot (_cli/_cli_completion.py:1271-1301) hashes every required_outputs descriptor, so it returns None after any curation write.
  • aggregate_proof_is_current (sdk_/_run_state.py:1415-1433, exported) skips the GUI-written descriptors in _GUI_WRITTEN_PROOF_DESCRIPTORS (:1331-1333, checked at :1369-1371).

The waiter's _published uses the strict one as its third disjunct (_cli_wait.py:238-242).

The readers rule. _gui/CLAUDE.md ("Importing readers: sdk_, not _cli") makes a new _cli import that answers "is this run finished?" a regression, and docs/source/contrib_guide/tracked_state.md:496 says a GUI consumer imports from sdk_ only. The no-cancel flag (I5, N2). _reconcile_submission gains a keyword cancel_inactive: bool.

  • True (the timeout and stream-error arms only): an inactive fence is cancelled as today (_slurm.py:652-656).
  • False (exit 4 with no job set): an inactive fence returns "no jobs" at once, without reconciling its ledger or scheduler comments. PA4. Exit 3 reads "complete, N images failed"

Behaviour. A run that the verdict below confirms gets the terminal registry status complete_with_failures and a count failed_images = N. The verdict requires that:

  • every accepted image is resolved;
  • at least one failed terminally;
  • the run's aggregate publication still covers the run as it now stands, or, for an all-failed run, none exists (D16, PA4 step 4).

N is the number of failed verdicts in state.images (the count diagnostics.failed reports, which nothing branches on). It agrees with the CLI's exit code on zero/non-zero, but it can differ in value: the CLI uses this invocation's count when positive (_run_failure_count, phenotypicCLI.py:1493-1518). The GUI shows the run's count (review Minor 4).

It is shown in four places:

  • Recent Runs: complete · N failed.
  • The status banner (update_log_tail, run_console/_callbacks.py:2581-2622): the same text.
  • The no-dashboard message (:2549-2560): the same text.
  • The results-viewer and analysis snapshot badge (D3). In snapshot_refresh_status (_gui/_snapshot_status.py:53-98) the new arm does not return before the currency check, as the unfinished arm does (:84-91). It falls through to snapshot_is_current (:92-98). A confirmed run with a current snapshot reads "Run complete · N images failed" (warning); one that is not current reads "Changed on disk", as a complete run does (review I4). This keeps the module's CAN-18 rule (:3-9). _UNFINISHED_BADGE (:47-50) keeps its two literals, so test_every_completion_literal_has_a_badge still binds it.

The verdict: one sdk_ function, the failed-run twin of rule 1 (C1, I1). run_finished_with_failures(state: RunState, output_dir: Path) -> int | None, in sdk_/_run_state.py beside _run_proof_covers_current_inventory (:1464-1541) and exported from phenotypic.sdk_ (N1). It returns N, or None, from the caller's own RunState and the aggregate proof beside it. It does no resolve_run_state of its own, so each caller judges the state it already resolved, at its own depth:

  1. Completion. completion == "failed": no live authority, and at least one image failed (:1922-1934).

  2. Resolution, over state.images. Every accepted image's verdict is verified or failed; none is unresolved. It is stated over the per-image verdicts, never over diagnostics, which nothing may branch on (sdk_/_state_types.py:138-150; plan review I1). N is the number of failed verdicts.

  3. The proof arm (at least one image verified). _valid_aggregate_proof(output_dir), the GUI-tolerant check behind aggregate_proof_is_current (:1397-1433), is not None. Never valid_aggregate_snapshot, whose strict hashing a curation write defeats (§3.2). Then clause 2 of rule 1, against that proof, the same comparisons _run_proof_covers_current_inventory makes against the run proof:

    • proof["inventory_digest"] == state.identity.inventory_digest;
    • proof["scientific_config_digest"] == state.identity.scientific_config_digest;
    • proof["finalization_input_digest"] in state.finalization_digests (see "Where the config comes from" below);
    • proof["source_set_digest"] == canonical_digest(sorted(verified work ids)), and proof["source_image_count"] == len(verified). The aggregate proof carries both directly (_cli_completion.py:1258-1259).

  4. The no-proof arm (D16) (no image verified). An all-failed run can have no aggregate proof: publish_aggregate_snapshot refuses zero successes (_cli_completion.py:1179-1181). In place of the proof's digests the arm requires:

    • every accepted image's verdict is failed. resolve_run_state matches failure records against the current inventory's work ids, which bind the processing configuration and the input (_cli/_cli_failure_tracker.py:276, 507), so a changed configuration or input set leaves an image unresolved rather than failed, and step 2 already refuses that;
    • completion == "failed" (step 1), so no liveness authority claims the run. A first run killed mid-image leaves that image unresolved. A killed --retry-failures relaunch that verified nothing leaves every earlier failure row in the append-only journal (_run_state.py:995-996), so the run reads confirmed again, unchanged; that is benign, and it stays claimable (PA11, N7);
    • no aggregate publication marker file exists, tested by path: aggregate_publication_marker_path(output_dir).exists() is false. Never through _valid_aggregate_proof, which returns None alike for an absent, wrong-version, empty or tampered marker (_run_state.py:1350-1377; plan re-review R2-I2). A marker of any kind beside zero verified images is not a finished all-failed run;
    • no deliverable from another generation: neither master_measurements.parquet nor measurements.parquet exists under deliverables/. An all-failed finalize writes no deliverable: locally it returns before writing ("No valid measurements found", _cli_finalize_run.py:883-885), and a SLURM finalizer logs and closes the lifecycle terminal-incomplete (_cli_checkpoint_handler.py:317-331). Such a tree reads failed, not finished. A plain re-run, another --restart, or a --retry-failures that verifies nothing leaves it so. What clears it is --overwrite, or a --retry-failures run from the CLI that verifies at least one image, which then publishes a proof and moves the run to the proof arm (plan re-review R3-I2). The claim gate says exactly that (PA11).

    No finalization input is compared: nothing was published, so nothing can be stale. N is the number of accepted images.

A killed relaunch can only be resumed from the CLI (N7), if it verified something. Suppose a GUI-launched --retry-failures (or plain Run) relaunch on a confirmed output is killed before it finalizes. If it verified at least one image, the source set no longer matches the proof (or, for an all-failed run, an image is now verified with no proof), so the output is an unconfirmed failed run, and this gate refuses it, as D10's "still refuses … unfinished" requires. If it verified nothing, every earlier failure row is still in the journal and the proof (if any) still covers the run, so the output reads confirmed again, unchanged, and stays claimable (plan re-review R2-I2). The GUI's own relaunch is what strands the user on the CLI, so the refusal message and the tutorial (PA7) both say to re-run the same command from the CLI.

A local CLI run is invisible to the gate (D17). The liveness authorities are the SLURM fence and a GUI owner with a live pid (sdk_/_run_state.py:1078-1140); a local CLI process holds neither, and the CLI takes no output-wide lock (its one exclusive_path_lock guards the metadata snapshot, phenotypicCLI.py:1255-1268). So the GUI can claim a confirmed output that a local CLI process is re-running at that moment. This is accepted and documented: the tutorial (PA7) and the run docs (PA8) say not to run the same output from the CLI and the GUI at once.

The refusal message for an unconfirmed failed run no longer calls a GUI-launched run "non-GUI". It says "output has an unfinished run with N failed image(s) of M accepted; re-run it from the CLI or wait for it to finish".

The stale-deliverables case has its own message (plan re-review R3-I2).
